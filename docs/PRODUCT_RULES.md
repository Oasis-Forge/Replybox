# Product rules

_21 September 2026._

This file defines how Replybox behaves: the calculations, defaults, and edge cases behind each screen. Where a competitor was studied (see `docs/research/competitor-analysis.md`), a section says what they do, what we take from it, and our rule: we learn from their app; we don't copy its rules. Where none was, a section starts from the user need instead.

- Rule IDs (`DATA-1`) are stable: never renumber or reuse one. A dropped rule stays, struck through, with its date and reason. Tests, code comments, PRs, and roadmap items reference them.
- A rule is testable: a number, a default, an order, an edge case. "Entry is fast" isn't a rule; "a basic entry takes about four taps" is.
- "Not verified" marks competitor behavior we saw only partly.
- Every rule keeps the product principles in `CLAUDE.md`: 1. Nothing leaves the phone: no account, no server, no analytics, no internet permission in the release build. 2. Free is complete: inbox, reply, waiting list and search never move behind a payment. 3. Honest about limits: the app says what it cannot see. 4. Never hides or answers another app's notification unless the user asked. 5. Two taps to reply or clear.

## Section shape

`/spec <area>` writes a section in this shape:

> ## N. Area
>
> **They do:** what the competitor does, in our words. Parts we couldn't check: not verified.
>
> **Learn:** the user need behind it, and where they fall short.
>
> - **AREA-1** Our rule.

With no competitor studied (`docs/research/competitor-analysis.md` records that, dated), a section has no **They do** and opens with **Learn**, written from the user need itself. Never write a **They do** from what a competitor is assumed to do: the rules below it would then cite a guess as observed fact.

The sections below are starter rules that held up in an earlier app. Keep, change, or delete each one, and record the choice under Decisions.

## 1. Data foundations

**Learn:** undo, trash, backup merge, sync, and translations all depend on these being right before any user data exists.

- **REC-1** Every record has `created_at` and `updated_at`.
- **REC-2** Every record ID is a UUID v4, so records from a backup or another device never collide. Built-in defaults use fixed IDs instead, so the same default matches across devices.
- **DEL-1** Deleting sets `deleted_at`; it doesn't remove the row. Deleted records count nowhere: totals, charts, search, or export.
- **DEL-2** Delete needs no confirmation. A snackbar offers Undo for about 5 seconds. Deleted items stay in the trash for 30 days, then get purged on app start.
- **DATA-1** User-facing names of built-in items (default categories, default accounts) are translatable labels referenced by ID, never stored text.
- **MONEY-1** If the app handles money: amounts are integers in thousandths of a unit (`12.50` → `12500`), so sums never drift and every ISO currency fits. The record's type carries the sign.
- **DATE-1** A date the user picks is a local calendar date. It stays on that date if the device's time zone changes later.

## 2. Backup and export

**Learn:** a raw database file breaks across schema versions, and defaults that send data off the device cost trust.

- **BAK-1** A backup is a file with the app version and the schema version, saved or shared only when the user chooses to.
- **BAK-2** Before a restore replaces or merges anything, the app saves an automatic backup of the current data.
- **BAK-3** Merge matches records by ID (REC-2); the later `updated_at` wins, deletions included (DEL-1). The app then shows how many records were added, updated, and unchanged.
- **BAK-4** A backup from a newer schema is refused with a message to update the app. Older backups are migrated with the app's own schema steps.
- **BAK-5** Exported files use ISO dates and plain decimals with a `.`, whatever the language. Spreadsheet text starting with `=`, `+`, `-`, or `@` gets a leading apostrophe.

## 3. First run and trust

**Learn:** asking for an account, permissions, or cloud backup up front costs trust before the app has earned any.

- **RUN-1** An empty screen explains itself with one clear first action.
- **RUN-2** The release build declares no permission a shipped feature doesn't need, so the store's data-safety answers stay true. The release workflow checks it.
- **RUN-3** The first launch asks only what the device can't tell (for example the language and currency) on one page, preselected from the locale. Permissions are requested when the feature that needs them is first used, and everything else works if they're refused.
- **RUN-4** A walkthrough of up to four pages follows setup. Every page has Skip, it respects reduce motion, it can be replayed from Settings, and it shows once. An update on a device that already has data skips setup and the walkthrough.

## 4. Languages

**Learn:** a translated app only feels native when numbers, dates, plurals, search, and layout direction are right too. A cut-off label looks broken.

- **LANG-1** The app follows the device language and falls back to English. Settings offers "System default" and each language in its own name. A change applies without a restart.
- **LANG-2** Every user-facing text comes from the message files, including notifications, widgets, and generated files. Plurals and variable parts are ICU messages, never pieced-together strings. CI fails on a missing message or mismatched placeholders.
- **LANG-3** Dates, numbers, and amounts follow the chosen language's format. Files the app writes don't (BAK-5).
- **LANG-4** Search ignores case and accents in every language, including the Turkish dotted and dotless i.
- **LANG-5** Right-to-left languages mirror the layout: navigation, lists, swipe actions, arrows. Amounts, numbers, and expressions stay left to right inside them.
- **LANG-6** Translations are machine-made in the same PR that adds or changes the English message. Widget tests render the main screens in every language on a phone-size screen at 1.3× text size, and fail on overflow.

## 5. App lock

**Learn:** private data needs a lock, but a forgotten app PIN locks people out of their own records.

- **LOCK-1** App lock is off by default and uses the device's own biometrics or screen lock, so the app never stores a PIN. Turning it on or off asks for authentication first.
- **LOCK-2** With app lock on, the app asks at launch and after at least a minute in the background, and hides its content until unlocked. Notifications and widgets show no private data.
- **LOCK-3** If the device no longer has biometrics or a screen lock, app lock turns itself off instead of locking the data away.

## 6. Plus and paying
<!-- The app is free and carries no ads. A one-time "Plus" purchase unlocks the capabilities listed in docs/PLAN.md section 3. Name the screens and the locked capabilities when you /spec this section. -->

**Learn:** an ad SDK collects device identifiers and needs the internet permission, so ads would turn "nothing leaves the phone" into a false answer on the Play data-safety form and cost the app the one claim nothing else in the category can make. The free tier therefore pays for nothing, and the upgrade has to be worth buying on its own merits. A subscription to *not* see something is resented; what is sold must already work.

- **PAY-1** Plus is a one-time non-consumable purchase, not a subscription, and it unlocks every Plus capability at once. It follows the store account, "Restore purchases" sits beside the price, and the app asks the store what is owned at each launch, so a refund or a family-shared purchase lands without a reinstall.
- **PAY-2** Prices come from the store, in the buyer's currency. Never hard-coded, and nothing to do with any setting in the app.
- **PAY-3** Nothing is sold before it exists. A Plus capability that isn't finished is shown as "coming soon", with no price and no button.
- **PAY-4** Nothing that already works moves behind a payment. Paying adds what is new: the inbox, reply, the waiting list and search stay free whatever else changes (product principle 2).
- **PAY-5** Selling is quiet: one row in Settings and one small "Plus" tag on a locked capability. No interstitial upsell, no countdown, no trial that lapses into a charge — and no ad of any kind, in any build, anywhere in the app.
- **PAY-6** A purchase that fails or is left pending never charges twice and never leaves the app half-paid: the app finishes every purchase with the store whatever the outcome, including the purchase sheet being closed without buying, and nothing unlocks until the store confirms it. A store with no such product configured is a real state — show "nothing to sell yet" rather than a button that only fails.

## 7. Capture

**Learn:** the person has one phone and several apps shouting at it. What they want is not another notification log — it is to open one place, see who is waiting on a reply, and answer without hunting through six icons. What makes that tedious today is that every app keeps its own inbox, and the only thing they share is the shade, which is a pile that clears itself. The app can only ever see what the phone showed it, so the whole area turns on being exact about that boundary: capture faithfully, say plainly what is missing, and never guess at content it did not receive.

Rules marked provisional rest on behaviour measured against one app on one API level; CAP-25 says what takes the mark off.

- **CAP-1** The app stores a notification only from an app whose row in the included list is on, and the listener drops every other package before anything reaches the native queue. An app in the shipped messaging-app list (`docs/PLAN.md` section 1) is on the first time it posts a notification the listener sees; every other app is off until the user turns it on. Turning an app off stops capture from it at once and leaves what it already captured in the inbox (product principle 4).
- **CAP-2** (provisional, spike check 1 — CAP-25) A notification becomes a message only when its `template` is `android.app.Notification$MessagingStyle`. A notification from an included app with any other template is never guessed into a sender and a text: it is either kept under CAP-21 or ignored, so a promotion, a delivery update or a "backing up your photos" notice is never filed as a message. Confirmed on Google Messages and on shell fixtures at API 37 only; the other five target apps were untested (spike, 21 September 2026, check 1).
- **CAP-3** A conversation is identified by the app's package plus the first non-empty value of `shortcutId`, `conversationTitle`, `tag`. A value of `""` counts as absent, because redaction empties title fields (CAP-8); a notification supplying none of the three is keyed by its own notification `key` and never merged into another conversation. `groupKey` is never a conversation key: in the spike's dumps one `groupKey` covered three separate Google Messages threads and three separate shell threads, and one notification's `groupKey` changed between its post and its removal (spike dumps, 21 September 2026). The resolved key, the field it came from, and the other candidates seen are stored beside the conversation, so an app that changes its keying is migrated rather than split silently. Which of `shortcutId` and `conversationTitle` wins is provisional (CAP-25): no notification the spike captured carried both.
- **CAP-4** (provisional, spike check 1 — CAP-25) Every message in the notification's message history is stored as its own message with its own sender and time, not only the visible line: in a burst the visible `text` collapses to the newest message while the history keeps them all, and the inbox shows all of them. Measured on a shell-posted fixture; the one real app in the spike posted one notification per message and never a growing history (spike, 21 September 2026, check 2, fixture `shell-burst.jsonl`), so how each target app bursts is unmeasured.
- **CAP-5** A message is stored once. Inside one notification `key` what makes it that message is **its place in the order of that notification's message history**, aligned against the history already stored under that key; across notification `key`s it is its content. Neither is its position and neither is the clock it happens to be carrying now. See the fourth correction below, which is the current rule; the paragraph after it is the wording that correction replaces, kept because the reasons in it still hold.

  **Correction, 21 September 2026, fourth — a history is a list, and identity is a question about the list.** The three corrections below all asked "is this entry the same as *some stored row*?", and answered it by matching a tuple of fields. A device moved whichever field the current answer trusted, twice over, and all four of the owner's replies were stored twice (drill, emulator-5554, API 37, 21 September 2026, evening). Two shapes did it, both in `docs/research/spike-dumps/2026-09-21-shipped-projection-evening.jsonl`: a post in which **the window slid and the entry's clock moved at once**, so the content shape missed on the time and the position shape missed on the index; and a post in which **the moved entry was still the newest line of its history**, which is exactly where the position shape was forbidden to look. On a phone with a real recipient there is no SMS loopback echo to push the owner's line out of the newest slot, so the second shape is likely the ordinary case rather than the rare one — an inference from the emulator's loopback, not a measurement.

  So the question changes. When a notification posts again under a `key` we have seen, what arrives is the history we saw before with entries possibly dropped from the front and entries possibly appended to the back — a window. The incoming history is **aligned** against what is stored for that key, the way a diff aligns two files: the longest run at the end of what is stored that is also a run at the start of what arrived. Entries that align are the same messages, whatever their index or their timestamp now says; entries left over after the alignment are new. A genuine repeat — "ok", then "ok" again — is an extra element at the end that the alignment cannot consume, and so is stored, which is the case field-matching kept getting wrong in one direction or the other.

  What a pair is aligned on is what a window carries unchanged: the sender — with **no sender at all** (the owner's own line, INB-9) kept distinct from a sender Android emptied (CAP-8), which the stored `direction` is what tells apart — and the content hash, which is the text where there is text and the attachment's type code where there is not (CAP-9). Not the index. Not the time. The stored side is read as a bounded tail: `MessagingStyle` retains 25 entries, so an overlap can never be longer than 25, and the tail is **50** — one extra history's worth of room, because the hand-over queue is not always drained in order and an older post can leave a whole history sitting past the overlap.

  **One thing is asked of the clock, and it is corroboration rather than identity: an alignment counts only if at least one of its aligned pairs still agrees on `sent_at` exactly.** Without that, an alignment cannot be told from a fresh window carrying the same words, and folding those together loses a message. A re-post re-presents lines already seen, and an app moves the clock on the line it has just refined and not on the ones above it: every post in the drill that moved a clock still carried five other entries whose times had not moved. Where there is no such anchor the alignment declines and the entry is stored again.

  **Which applies when.** Alignment is the rule *within* one notification `key`. The content match — conversation, `sent_at`, sender and content hash, at any position and under any key — is the rule *across* keys, for an app that posts one notification per message under distinct keys (Google Messages does this for incoming messages) and for a reconnection re-read that hands a message back under a new key (CAP-13). It also runs over whatever the alignment leaves inside the same key, because an *older* post of a key redelivered after a newer one has its overlap in the middle of the stored list rather than at the end, where no alignment can find it. That boundary is where the next defect will live.

  **Residuals, accepted, and every one of them falls to a duplicate rather than a loss** — a duplicate is a line the user can delete; a loss is a message they never see, which is the lesson of the three corrections below. A notification whose *whole* history moved its clocks with nothing unmoved left in it — in practice a history of one entry, re-posted with its time moved and nothing appended — has no anchor and is stored again. Two identical texts from one sender at the same millisecond arriving under two *different* notifications are stored once, and so are two attachments of one type in the same position, because the cross-key match has only content to work with (CAP-15 keeps an attachment's type code and never the MIME string behind it).

  **What the schema can no longer say.** A message that carried its own time has **no unique index** any more. The alignment deliberately allows two rows of one conversation to agree on `sent_at`, sender, content hash *and* `history_index` — a window that slides an entry down while a new entry with the same words takes the position it left is exactly that — so a unique index over those columns would reject a write the rule allows, and an index that over-rejects does not protect a message, it deletes one. The one unique index left covers the messages whose identity genuinely is a tuple: those with no time of their own (CAP-8, CAP-21), keyed on their notification and their position.

  **The wording this replaces, 21 September 2026, third and earlier.** A message is stored once, and what makes it that message is its content, never where it sat. Two messages are the same when their conversation, sender, text and `sent_at` all match — at any position, in any notification, under any `key` — `sent_at` being the time the posting app gave the message and never the time we captured it (REC-1's `created_at`); a message with no text is matched on whatever content it does carry — an attachment on its type code (CAP-9), which a sliding window carries with it — and only a hidden message, which carries none at all, falls back to the identity CAP-8 gives it. That one match covers a re-post, a reconnection re-read (CAP-13) and a history window that slides. The burst is what forces it to be content and not time: the spike's burst delivered five messages under one identical timestamp (spike dumps, 21 September 2026), so time cannot separate them on its own — but time with sender and text can, because those five messages carried five different texts. Inside a single notification's message history the position is the tie-break and nothing more: two entries identical in all four fields are two messages and are stored as two, because a history that shows "?" twice is showing a message sent twice. `history_index` is still stored — where a message sat is worth knowing, and it is what keeps those two rows apart — and it is not identity. The lookup sees soft-deleted rows (DEL-1): a message the user deleted is not stored again by a re-post or a re-read, and never reappears in the inbox. Two residuals, accepted. Two identical texts from one sender at the same millisecond arriving under two *different* notifications are stored once. And two attachments of one type from one sender at the same millisecond arriving under two *different* notifications are stored once: an attachment is matched on its type code because that is all of it the app is given, and CAP-15 keeps the code and never the MIME string behind it, so two photos that far apart on nothing else cannot be told apart. Both are the price of matching on content, and it is the right way round: the alternative — matching on position — cost a message every time a window slid, which is what the correction below is about.

  **Correction, 21 September 2026, third — the entry's own clock moves too.** The correction below takes `sent_at` out of identity for a message that never had one. The clock a message *did* carry moves as well, on the app the whole product is measured against: Google Messages posted one notification twice, 501 ms apart, and moved the history entry's own `time` between the two posts — same conversation, same notification `key`, same position, same sender, same words, two rows, and the user's own reply drawn twice in their thread (device drill, emulator-5554, API 37, 21 September 2026). So for a message that carried its own time, a stored row is that message when **either** shape holds: its conversation, `sent_at`, sender and content, at any position (a window that slides changes the position and not the time); **or** its conversation, notification `key`, position, sender and content, at any time (a re-post changes the time and not the position). The second shape is read **only for an entry that is not the newest line of the history it arrived in**, and that restriction is the whole safety of it: a contact who sends "ok" and then "ok" again to a thread whose notification carries one entry hands us two different messages at one position under one key, and folding those together would lose the second — the failure the correction below exists to stop. A genuinely new message always arrives at the newest position of the history it arrives in; one that a newer line has pushed down the window has been seen before. It is the same discriminator CAP-8 already uses, for the same reason. Two residuals, accepted and stated. A window that slides **and** whose clock moves at once matches on neither shape and is stored twice; nothing in the data can tell that apart from a new message, and no dump holds one. And a notification re-posted with its newest entry's clock moved and nothing appended after it is likewise stored twice, which is CAP-8's residual reached by another road: the cost is a repeated line the user can delete, and the alternative costs a message they were sent.

  **Correction, 21 September 2026, second.** `sent_at` identifies a message only where the posting app gave the message that time. Where it gave none — a hidden message (CAP-8), a raw one (CAP-21), an attachment or a text line whose entry carried no readable time — `sent_at` is the notification's `postTime`, and Android sets `postTime` afresh on every enqueue, including the in-place update an app makes when it re-posts a notification already in the shade. Matched on it, none of those rows was ever found again and every re-post filed the same message once more: an app calling `notify()` again with the same id — "2 new notifications", a group alert, an email summary — grew its thread by one row every time, for as long as it kept re-posting. Those messages are matched instead on the notification `key` and the position CAP-8 names, plus whatever content they do carry, and never on that time, so an unchanged re-post is the same message and a changed one is not. Which of the two rules a stored row is under is recorded on the row and never re-derived by a later read.

  **Correction, 21 September 2026.** An earlier version of this rule said that within one notification `key` a message's identity is that key plus its position in the message history. That is what the burst seemed to show, and it was wrong in the most expensive way available: Google Messages — the one real app the spike measured — posts one notification per message and reuses one key for the whole thread, each post carrying a history of one entry at index 0. Under the old wording the second message a contact sent collided with the first and was discarded, and so did every message after it. The app would have stored the first message a contact ever sent and nothing else, on the app most of its users have. The same wording lost the newest message of any sliding history window, because a window that slides hands a message a position an earlier read already used — which is the proof that position is not identity. The rule's stated reason survives intact: time alone still cannot separate a burst, and time plus sender plus the text is what separates it now.

- **CAP-6** A notification with `isGroupSummary` set is never stored as a message. Every group summary the spike captured carried an empty message history (spike dumps, 21 September 2026), so nothing is lost by dropping it; its children carry the content.
- **CAP-7** An ongoing notification is never stored as a message. It is a status, not something anyone is waiting on a reply to.
- **CAP-8** A hidden message is recognised from the notification's structure, never by matching the system's marker text, which is a system string that changes with the phone's language: a `MessagingStyle` notification whose message `sender`, `title` and `selfDisplayName` are all empty while its text is not. It is stored as hidden with no text, and shown with the app it came from, the notification's `postTime` as its arrival time, and only "open in app". Its identity for CAP-5 is the notification `key` plus its position in the history, never sender, text or the message's own time: that time was observed to move 19 seconds between two reads of one unchanged notification (spike dumps, 21 September 2026). A hidden notification also arrives with every action title emptied to `""`, so actions are matched by `semanticAction` and by carrying a `RemoteInput`, never by label. The marker is never stored as if it were the message, and the app never guesses what was hidden. Redaction could not be switched off on API 37 and has widened with successive Android releases, so the app treats it as a permanent condition of being a third-party listener rather than a setting a user can waive (spike, 21 September 2026, check 4, fixture `messages-redaction.jsonl`).

  **Correction, 21 September 2026.** Two phrases in this rule were written loosely enough to destroy data, and both are fixed here.

  *What "empty" means.* The structural test said the message `sender`, `title` and `selfDisplayName` are "all empty", and that was read as *empty or absent*. `MessagingStyle` marks the phone owner's own line by constructing it with a null `Person`, so `Message.toBundle()` writes neither `sender` nor `sender_person` and the key arrives absent — while INB-2 says a real notification can carry an empty title, and the spike's own redacted dump does. A line the **user** wrote on such a notification was therefore read as hidden: stored with no text at all, unrecoverable, and shown back to them as something their phone had hidden. The sender is now read the way this rule's own CAP-21 path already reads the title: redaction *empties* a value and does not drop the key, and the dump carries `"sender": ""` beside the marker (`messages-redaction.jsonl`). A sender that is there with no name is redaction; no sender at all is the user (INB-9). The residual runs one way only: a redacted notification whose sender key arrived absent rather than emptied is kept as an ordinary message, marker string and all, because destroying a message the app was handed is the worse error every time.

  *What identity means.* "The notification `key` plus its position in the history, never sender, text or the message's own time" left the notification's `postTime` unsaid, and `postTime` is exactly what a hidden message's `sent_at` is. Android sets it on every enqueue, including an in-place update of a notification already in the shade, so it moves under a message that has not changed — and with it in the match the stored row was never found, so every re-post filed the message again. **A time that moves cannot be part of identity**, so it is out of the match. There is one exception, and it is there to keep from losing a message rather than to be tidy: at the **newest** position of a history, a hidden message claims a stored row only when the phone posted it at the same moment. A reconnection re-read hands back the same notification with the same `postTime` and so stores nothing (CAP-13); a later post at that position is treated as a new message and kept. Nothing can tell the two apart on the data available — a hidden message carries no sender, no text and no time it can trust — and Google Messages posts every message of a thread under one reused key with a history of one entry at index 0, so reading that post as a re-post would store the first message a contact ever sent to a redacted thread and nothing after it, which is the failure CAP-5's correction exists to stop. The residual is therefore the other way round, and it is the cheaper one: a redacted notification re-posted with nothing new in it leaves a second "message hidden" row in the thread.
- **CAP-9** (provisional, untested — CAP-25) A photo, voice note or other attachment is stored as an attachment type code, never as the rendered words (DATA-1); the inbox renders that code through the message files, so the same record reads correctly after a language change or a restore (LANG-2). No media file is ever read or copied out of the other app. No attachment was captured in the spike (`docs/research/spike.md`, "When hardware arrives", item 3), so where a notification does not name the type, the placeholder says only that something arrived the app cannot show (product principle 3).
- **CAP-10** The app never posts, alters, hides or dismisses another app's notification unless the user asked for that action on that conversation (product principle 4).
- **CAP-11** A message being dismissed from the shade does not delete the stored message. The shade is the other app's; the inbox is ours.
- **CAP-12** The app has no history from before it was installed, none from while notification access was off, none from an app whose row is off (CAP-1), and no record of an edit, unsend or deletion made in the source app (CAP-26). Each of those absences is stated on screen where it would otherwise look like a bug (product principle 3, see RUN-1). The date the history begins is written on the app's first launch, on every platform and before any permission is granted, and never moves after. A capture window is one row: the listener binding while a window is already open opens no second one, because two open rows are the same window counted twice, not a longer record.

  **Note, 21 September 2026 — how a window ends when nothing says it ended.** `onListenerDisconnected` does not fire when the user revokes notification access at API 37; the process is torn down and nothing is delivered, checked with the app's Dart side dead so the hand-over queue could not have swallowed it (device drill). A drill that ran thirty binds finished with thirty open windows, and a rule read off that table would have told the user capture was continuously on across a window in which it was off — the one direction this rule may not be wrong in. So on launch, when access is off and a window is still open, the app closes it at **the newest arrival time of any message it captured inside that window**, and at the window's own start when it captured none. Every instant then claimed has a stored message standing behind it, and nothing past the last such proof is claimed; the app says capture has been off since at least that time. Claiming a shorter on-window than the truth is the safe direction and is what this produces. What it does not cover, stated rather than left to be found: a window that was interrupted and re-bound while access stayed on — a reboot, a force-stop, a crash — is recorded as one continuous window, because nothing in the data dates the interruption.

  **Correction, 21 September 2026 — the reconciliation runs after the drain, not before it.** On launch the app closed the stale window first and drained the listener's queue second, and the drain undid the close: it applied a queued `listener_connected` whose `postTime` predates the revoke, which opened a new window and left it open while access was off (drill, emulator-5554, API 37, 21 September 2026, evening — session `ece20736` correctly closed, session `775f246a` opened behind it). The next launch closed that one and opened another. So the order is: **drain first, so every lifecycle event the listener recorded while the app was dead has been applied, then settle the window against the access the app has right now.** Opening a window for a queued connect that really happened is correct — this rule is a record of what the listener could see, not of what the app noticed — and leaving it open when access is off is not. The one-window guard is unchanged and is what the device confirmed works: eight binds and five `listener_connected` events produced one row and one open window.
- **CAP-13** (provisional, spike check 3 — CAP-25) An event that arrives while the Flutter app is not running is appended to the native queue by the listener and handed over when the app next starts; on reconnection the listener re-reads `getActiveNotifications()` and reconciles it against what is stored, using CAP-5 to avoid duplicates. Neither half has been measured: the 24-hour OEM survival check did not run (spike, 21 September 2026, check 3), and the reconnection re-read is design (`docs/PLAN.md` section 4), not a spike result.
- **CAP-14** Whether a conversation can be replied to inside the app is a property of this run, not of the stored data: a `PendingIntent` cannot be serialised, so a reply action cannot be saved to disk. A conversation is repliable while its notification is held in this process — one that arrived since launch, or one still posted that the listener re-read on reconnection (CAP-13). Otherwise it shows "open in app". Dismissal alone never removes reply: a held action still delivered after every notification was cancelled (spike, 21 September 2026, check 5). That a restart clears the map follows from `PendingIntent` not being serialisable and was not itself measured (CAP-25).
- **CAP-15** Nothing the inbox cannot show survives normalisation. The app database keeps only the schema's fields (`docs/PLAN.md` section 4): for a message, its conversation, sender, text, `sent_at`, direction, content kind and notification key; for a conversation, its package, conversation key and the candidates that produced it (CAP-3), title and group flag. Icons, extras, channel and action objects are dropped at normalisation and never written. The native hand-over queue holds one JSON row per event carrying those same projected fields and never the notification's extras; a row is deleted in the transaction that writes its message, and a row still undrained after 30 days is dropped on the next service start.
- **CAP-16** A captured record follows the record rules: a UUID, `created_at` and `updated_at` (REC-1, REC-2), and deletion is soft (DEL-1) with no confirmation and about five seconds of Undo (DEL-2). Deleting a conversation soft-deletes it and every message in it in one step, and one Undo restores all of them; deleting a single message leaves the conversation standing.
- **CAP-17** A backup carries the included-apps list, the conversations and their messages, matched by ID on merge (BAK-1, BAK-3). A restored conversation is matched first on package and conversation key (CAP-3) and keeps the local row's ID, so its messages land in the existing thread rather than forking it or pointing at a `conversation_id` the device has never seen. Message text, sender names and conversation titles are written by whoever sent them, so every exported field goes through BAK-5's escaping, not only the fields the user typed.
- **CAP-18** With app lock on, a captured message's content is never shown in the app's own notifications or widgets, nor in the app's preview in the task switcher (LOCK-2).
- **CAP-19** Search over captured messages ignores case and accents in every language (LANG-4).
- **CAP-20** Capture adds no `uses-permission` to the release build. Notification access is a service declaration — `android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE"` on the listener `<service>`, naming the permission the system must hold to bind it — granted by the user in system settings, so it never appears in the app's requested-permission list. RUN-2's gate reads only `uses-permission` lines (`tool/check_permissions.sh`), so it never fires for capture: CAP-24 and CAP-27 are what cover capture, not that gate.
- **CAP-21** A notification from an included app that carries no `MessagingStyle` history is kept rather than dropped when its `category` is `msg`, `social` or `email`: one message of kind `raw` carrying the notification's title and text, in a conversation keyed by the package alone and labelled with the app's name, marked in the inbox as captured without a conversation. No reply is offered on it unless the notification itself carries a `RemoteInput`. Anything else from an included app is ignored (CAP-2).
- **CAP-22** A removal event is read as a signal about the source app, never as a change to our data (CAP-11). A removal with reason `CLICK` or `APP_CANCEL` marks the conversation read up to that notification's newest message and takes it off the waiting list; `LISTENER_CANCEL`, `LISTENER_CANCEL_ALL`, `CANCEL_ALL` and any unrecognised reason change nothing, because the shade being cleared is not the user reading anything. The reason comes from the removal event and is never inferred from the notification merely being gone.

  **Correction, 21 September 2026 — the shade's Clear all is `CANCEL_ALL`.** This rule used to cite the spike's `LISTENER_CANCEL_ALL` as the observed shade clear. It is not: that is what a *listener* produces by calling `cancelAll()` through the API, which is what the spike's own tooling did. Clearing the shade by hand arrived as `CANCEL_ALL` on every one of six removals (device drill, emulator-5554, API 37). The behaviour was never wrong — neither reason marks anything read, and both are listed above — only the sentence naming which one the shade sends. Observed to date: `APP_CANCEL` and `LISTENER_CANCEL_ALL` (spike), `CANCEL_ALL` (drill). `CLICK` and `LISTENER_CANCEL` are still unobserved.
- **CAP-23** A notification for a conversation the user deleted revives that conversation rather than opening a second row for the same package and key (CAP-3), and files the new message in it. Messages deleted earlier stay deleted (CAP-5, DEL-1): nothing the user deleted ever returns.
- **CAP-24** The release build sets `android:allowBackup="false"` and excludes the message database and the native queue in its `dataExtractionRules`, so Android's automatic cloud backup and device-to-device transfer never copy captured messages off the phone. This is the only path data can leave the device without the internet permission, so RUN-2's gate cannot catch it (CAP-20): the release workflow checks the built manifest the way it checks permissions, and fails on a change. The only copy that leaves is a backup file the user asked for (BAK-1, product principle 1).
- **CAP-25** A rule that rests on an app other than Google Messages, on a notification the spike never captured, or on the listener staying alive while the app is not running, is marked provisional and names the check it waits on. The discipline covers every section, not only this one; each section carries its own marks, and the list below stays capture-only. The mark comes off only with a dated result on hardware, never because the feature shipped. Every fixture records the `sdkInt` and release it was captured on, and a rule stating what Android hides names that level: behaviour measured at one API level is not assumed at another. Provisional today: CAP-2, CAP-3 (the order of its top two candidates), CAP-4, CAP-9, CAP-13, CAP-14.
- **CAP-26** The app stores the text it was handed when the notification arrived. An edit, an unsend or a deletion in the source app never reaches the listener, so a stored message can differ from what the conversation now shows. The thread view says so once, above the oldest message it holds, and the privacy policy says it too (CAP-27, product principle 3).
- **CAP-27** The PR that ships capture updates `docs/privacy-policy.md` in the same PR, and a capture PR that does not touch it does not merge: what is stored (sender, text, time, conversation, source app, the conversation key and its candidates, notification key, content kind), that these are messages other people sent and they stay on the phone, that automatic backup is off (CAP-24), that stored text can be staler than the conversation (CAP-26), and notification access with what still works if it is refused. The store's data-safety answers are refreshed from that same text.

## 8. Inbox

**Learn:** the inbox is where the promise is either kept or exposed. Someone grants a frightening permission and then wants one screen that answers a single question — who is waiting on me — and a second tap that answers them. What makes that hard here is not layout; it is that the list is assembled out of notifications, so it is only honest if it never implies more than it holds. A conversation the phone hid, a thread with no earlier history, an app that has been uninstalled, a reply action that died with the last process: each is a place where an ordinary chat UI would quietly lie by looking complete, and the user finds out at the worst moment, in a one-star review. So every rule below either fixes something a chat screen has to get right anyway — order, ties, unread, two taps — or names a gap on screen where a blank space would read as a bug (product principle 3, RUN-1).

This section also owns the included-apps list in Settings (INB-20 to INB-22), because the Inbox item ships before the Permissions item and cannot ship a Settings screen that does not exist yet. Everything the inbox says about notification access itself belongs to section 9 and is cited, never repeated. Rules marked provisional rest on behaviour no dated result covers; CAP-25 sets the discipline and names the checks.

- **INB-1** A row in the conversation list shows, in this order: a leading circle carrying up to two initials taken from the first two words of the conversation title and badged with the source app's icon (decision 7 — no avatars); the conversation title; a one-line preview of its newest message, truncated with an ellipsis rather than wrapped; that message's time; and, when it is not zero, an unread count (INB-5). A group conversation's preview is prefixed with the sender's name and a colon, a one-to-one conversation's is not (`conversations.is_group`). The time is the clock time for a message on today's local calendar day, the day name within the last seven days, and the short date beyond that, each formatted by LANG-3. The icon and label of a package inside INB-16's `<queries>` declaration come from the package manager; for any other package they come from the label the listener stored on its `apps` row (INB-20), and where neither resolves the row shows a generic source icon and the package name. The app never queries a package it has not declared.
- **INB-2** Where `conversations.title` is empty the row is titled with the source app's name, shows the app icon alone with no initials, and carries the message-files line `conversationUnnamed`, saying the notification arrived without a name. The branch is conditioned on the empty title and never on `key_source`: the spike's one redacted notification carried `shortcutId` `"1"`, an empty `title` and no `conversationTitle` at all (`messages-redaction.jsonl`, 21 September 2026), so a conversation can hold a resolved key (CAP-3) and no title at once. The line never attributes the missing name to redaction or to the app, because CAP-3 makes absent and emptied the same value and the app cannot tell which it is looking at.
- **INB-3** A hidden message (CAP-8) shows the message-files line `messageHidden` — that the phone hid this message's contents from the app and they can be read in the source app — as the row's preview and as its body in the thread; never the system's marker text, and never the emptied sender. Everywhere it is shown it carries the notification's `postTime` as its arrival time and never the message's own time (CAP-8), so the list and the thread never print two times for one message. While a conversation's newest message is hidden, the thread's bottom bar holds INB-13's control whatever the in-memory action map holds, and the line beside it says the app chose not to answer a message it cannot show: the spike's redacted notification still carried a working `RemoteInput` with `resultKey` `android.intent.extra.TEXT` (`messages-redaction.jsonl`), so this is a capability declined, not a platform limit (decision 8).
- **INB-4** The list sorts by `conversations.last_message_at` descending. That value is the newest message's `sent_at` for an ordinary message, the notification's `postTime` for a hidden one (CAP-8) and for a `raw` one (INB-12) — neither carries a message history to take a time from — and the moment the user pressed send for an outbound message not yet confirmed (INB-9). Ties are real: the spike's fixture delivered five messages under one identical `time` (`shell-burst.jsonl`, 21 September 2026), so two conversations can share a `last_message_at`. A tie breaks by `created_at` descending, then by `id` ascending — never by anything a later read could compute differently — and a test seeds rows with equal timestamps and asserts two reads produce the same order. Nothing in this area pins, promotes or reorders a conversation; a snoozed conversation returning (area SNZ) and a VIP sender (area RUL) do, and each states its own rule against this one rather than adding a second sort.
- **INB-5** A conversation's unread count is the number of inbound messages whose arrival time — the same value INB-4 sorts on, so a hidden message is counted by `postTime` — is newer than `conversations.read_through_at` (CAP-22), soft-deleted messages excluded (DEL-1), shown up to 99 and as `99+` beyond. A test seeds one hidden message and asserts two reads produce the same count. `read_through_at` only ever moves forward: an advance to a message older than the stored value, such as a late `APP_CANCEL` on an older notification (CAP-22), changes nothing. Opening the thread advances it to the newest message the conversation holds, whatever was scrolled. Reading is not answering: opening a thread never takes the conversation off the waiting list, which it leaves only when it is answered or explicitly marked done (area WAIT). The unread badge answers "is there anything new here" and the waiting list answers "do I still owe this person a reply"; a glance settles only the first, so the two can disagree and the waiting list says once, in its own empty state, that it is not a list of unread things. This is the one place a CAP-22 removal and an in-app read differ, and CAP-22's `CLICK` branch is what still clears both — reading it in the source app is a stronger signal than opening it here. A message arriving while the thread is open is marked read as it is drawn. Nothing else marks a conversation read, and the count never changes because the app posted, dismissed or altered a notification — it never does (CAP-10, INB-17).
- **INB-6** Swiping a row in the direction LANG-5 mirrors reveals one control and nothing else: Delete, at least 48dp on its shorter side. It soft-deletes the conversation and every message in it in one step, with no confirmation and about five seconds of Undo (CAP-16, DEL-1, DEL-2). During that window the row is gone from the list, from every filter and from its chip's count (INB-14), and Undo puts all of it back; a chip whose app's last conversation is inside a pending Undo stays in the row until the window closes. This swipe is the only delete in the list: nothing deletes on a long press, and nothing deletes from the thread's header.
- **INB-7** (provisional, spike check 1 — CAP-25) A thread shows messages oldest at the top and newest at the bottom and opens scrolled to the newest. Messages sort by arrival time ascending, then by the arrival order of the notification that carried them (`created_at` ascending), then by the message's index in that notification's history (CAP-5), then by `id` ascending — never by anything a later read could compute differently. One seeded-rows test, with two notifications sharing one `sent_at`, covers this and INB-4 together. A message arriving while the thread is open is appended in place: the view stays where the reader left it unless the newest message was fully visible when the new one arrived, in which case it follows. The only burst anyone has measured is a shell-posted fixture; the one real app in the spike posted one notification per message and never a growing history (CAP-4, spike, 21 September 2026, check 2).
- **INB-8** A date separator sits before the first message of each local calendar day, computed from the message's arrival time in the device's current time zone — not a stored calendar date, so a message re-groups under a new separator if the zone changes. DATE-1 governs a date the user picks and does not apply here. Each message carries its own arrival time, formatted by LANG-3 (INB-3 for a hidden one), and an inbound message shows its sender's name in a group conversation and not in a one-to-one.
- **INB-9** (provisional, spike check 1 — CAP-25) An outbound message sits on the side of the thread LANG-5 mirrors away from inbound ones, carries no initials circle, and carries a send state in (`pending`, `sent`, `failed`) — a Phase 1 column beside `direction` (CAP-15). While `pending` its text draws at the theme's disabled-text colour with a clock glyph in place of its time, it is never drawn as sent, and it counts towards `last_message_at` at once, so answering a conversation moves it to the top of the list before the send confirms (INB-4). A message's direction is read from the notification's own message history and never assumed. `MessagingStyle` has two ways of saying the phone owner wrote a line and both are read: the entry names the user — the name the notification carries in `selfDisplayName` — or the entry carries **no sender at all**, which is the platform's own convention for the current user's message and writes neither `sender` nor `sender_person`. The second cannot be read on a notification that names no user, and a sender Android emptied (CAP-8) says nothing either; where it cannot be decided the direction is stored as a third value, the message is drawn with no side and no sender rather than guessed into one, and it is counted in no unread badge (INB-5). Undecided is a value on the row, not the absence of one, or the guess comes back the moment anything has to be written. No dump holds a history line the posting user wrote, so how each target app marks its own lines is unmeasured.

  **Correction, 21 September 2026.** This rule named the undecided state and nothing made it storable: `direction` allowed two values, so capture had to pick one, and it picked inbound. Meanwhile the only test for outbound compared the entry's sender against `selfDisplayName`, and the platform's convention makes that sender *absent* — an absent sender equals nothing, so the branch was unreachable for exactly the messages it existed to catch. Every message the user had sent was stored inbound with an empty sender and counted in the user's own unread badge, and on a notification carrying no title and no `selfDisplayName` it was read as hidden and its text destroyed (CAP-8's correction). A third direction is now a real stored value and the badge counts inbound only. Area REP owns sending, the state transitions and the failure path; this rule fixes the shape they fill.
- **INB-10** Every thread's first row, above its oldest message, is a standing notice — not dismissible, not a one-time tip — saying the app holds only what arrived as a notification, and that a message edited, unsent or deleted in the source app still reads here as it first arrived (CAP-26). It names the date the app could first have seen anything for this conversation: the latest of `installed_at`, the first `capture_sessions` bind, and the start of the earliest `app_capture_sessions` row for this source app (CAP-1, CAP-12). Where no session existed before that date it says access was off until then. Where a later gap in either table overlaps this thread's range it names the most recent gap and a count of the others, counting only gaps longer than 60 seconds, so a rebind at boot is not reported as an absence anyone noticed. Where a retention window is in force (area RET) and is later than that date, the notice names the window instead and says the app once held older messages here and removed them, rather than leaving a date on screen beside a thread that no longer reaches it. Scrolling to the top never loads older messages and never shows a spinner suggesting there are any.
- **INB-11** (provisional, untested — CAP-25) A message whose `content_kind` is not `text` renders as a placeholder from the message files, never as stored words (CAP-9, LANG-2): one line each for `image`, `voice`, `video` and `file`, and for `other` the line that says only that something arrived the app cannot show. The same line is the row's preview when such a message is newest. The placeholder carries no size, duration, filename or thumbnail, because CAP-15 keeps none of them, and its second tap is INB-13's control. No attachment was captured in the spike (`docs/research/spike.md`, "When hardware arrives", item 3), so which kinds a notification actually names is unmeasured.
- **INB-12** A raw conversation (CAP-21) never reads like a chat, so nobody concludes the app lost the words. In the list its title is the source app's name, its leading circle is the app icon with no initials, its preview is the notification's title and text joined by ` — ` from the message files — or whichever of the two is non-empty, with no separator drawn — and it sorts by INB-4 like any other row. In the thread each raw message is a full-width note with its arrival time rather than a bubble attributed to a sender, under a standing line saying the app saw a notification from this app but not a conversation, and that the line below is the notification's own title and text as the phone delivered them, with nothing inferred and nothing added. Where the notification carried a longer body than the line stored, the same line says the app kept what the notification showed and the source app holds the rest: the app never claims the text is complete (product principle 3). A raw conversation never merges with a conversation keyed by CAP-3, because it is keyed by the package alone.
- **INB-13** (provisional, spike check 3 — CAP-25) Where a conversation has no live reply action (CAP-14), and whenever its newest message is hidden (INB-3), the thread's bottom bar holds an `Open in app` control in place of a reply field: full width inside the bar's 16dp gutters and 48dp high, which is the bar the reply field will occupy (area REP), so the second tap is in the same spot in either state (product principle 5). Opening goes through the `AppLauncher` service by exactly one of two paths and the label says which: with that conversation's notification held in this process the app fires the notification's own content intent, from the same in-memory map that holds CAP-14's reply actions, and the control reads `Open chat`; otherwise it starts the package's launcher intent, the control reads `Open <app>`, and the app claims nothing about where that lands. Neither intent carries an extra, a message, a sender or a conversation identifier the app added, and the app never builds an intent into another app's internals and never guesses a deep link (product principle 1). Firing a content intent may make the source app cancel its own notification; the removal that follows is read by CAP-22 like any other and marks the conversation read — that is the user having opened the chat, not the app dismissing anything (CAP-10), so INB-5's count changing after `Open chat` is this rule and not a bug. A launch that throws or resolves to nothing changes nothing on screen and leaves any typed text untouched: one snackbar, for about five seconds, says the app could not be opened. How many conversations still hold a live action or a content intent after a cold start depends on the unmeasured reconnection re-read (CAP-13), so no rule and no screen states a number or a proportion.
- **INB-14** Above the list sits a horizontally scrolling chip row with `All` pinned at its leading edge and one chip per source app with at least one conversation the list can show, ordered by that app's newest message and then by package ascending (INB-4). App chips are multi-select, and `All` is selected exactly when no app chip is. A filter is a view: it hides rows, changes no `enabled` flag (CAP-1), captures nothing differently and deletes nothing. A selected chip stays in the row after its app's last conversation is deleted and leaves the row the moment it is deselected or on the next cold start, whichever comes first — that is how INB-15's filtered-empty state is reached. The selection survives a backgrounding and resets to `All` on every cold start, so a forgotten filter can never make the inbox look permanently empty.
- **INB-15** The inbox has three empty states about its own data, and each explains itself with exactly one action (RUN-1). *Nothing yet*: nothing is stored — it names up to three included apps by label, most recently seen first, and a count of the rest; it says only messages arriving from now on can appear, that there is no history from before install, and, where a `capture_sessions` gap exists, that nothing was seen while access was off (CAP-12); its one action opens the included-apps list (INB-20). *Nothing in this filter*: a chip selection matches no conversation — it names the selected apps; its one action clears the filter back to `All` (INB-14). *No results*: a search returned nothing — it repeats the words searched, truncated to 60 characters with an ellipsis, and names any narrowing in force; its one action removes that narrowing, or clears the search when none is in force, and area SRCH fills its shape. Where more than one condition holds the first in that order wins. No empty state offers two buttons and none of them is blank. Notification access is not an empty state: PERM-8's banner draws above the rows when conversations are stored and replaces *Nothing yet* when none are.
- **INB-16** (provisional, untested — CAP-25) A conversation is never deleted, hidden or emptied because its source app was uninstalled: the messages are the user's and only the user deletes them (DEL-1, CAP-16). The manifest's existing `<queries>` element gains INB-20's shipped packages beside the entries the Flutter engine already requires — a manifest element, not a `uses-permission`, so like the listener's service declaration it never reaches RUN-2's permission list (CAP-20), and the release workflow checks the built manifest's `<queries>` against that constant the way it checks `allowBackup` (CAP-24). For a package inside the declaration the app can tell installed from gone: a gone app's row keeps its title and messages, falls back to a generic source icon, carries the message-files line `sourceAppGone`, and shows that line in place of INB-13's control. For any other package the app cannot tell, so it says less rather than guessing: the row keeps `Open in app`, and a failed launch reports only that the app could not be opened. The app never tells the user an app is uninstalled unless it can see that it is. No package-visibility behaviour was exercised in the spike, including whether a bound listener resolves a label or icon for a package outside `<queries>`.
- **INB-17** Reading in the inbox changes nothing in the shade, and a hand test asserts it: open a thread from the inbox, and the source notification is still there afterwards. Opening, scrolling, filtering and marking read (INB-5) are all reads. Nothing goes back to another app except an action the user asked for on that conversation (CAP-10); in this area that is one thing, INB-13's launch, and area REP adds sending a reply. No element of a row or a thread states or implies that a message was delivered, seen or read by anyone else: every time and every marker the inbox draws is capture-side, and the app holds no receipt from the source app to show.
- **INB-18** From whichever tab a cold start opens on (INB-19), with the conversation visible on it and without scrolling, replying takes two taps — the row, then send — plus typing, and clearing takes one, the row's Delete control (INB-6), with Undo as an optional second. A tap means a tap on a control: typing, scrolling, the swipe that reveals Delete, and dismissing a snackbar do not count. No confirmation dialog stands after either. A conversation on the other tab costs the tab tap first, and the test counts from both tabs and asserts two taps from the tab the conversation is on. Until area REP ships, the second tap of the reply path is INB-13's control. A widget test counts the taps on a seeded list rather than merely asserting that the controls exist.
- **INB-19** The selected tab is never stored: the app opens on the leading tab at every cold start and keeps a selection only across a backgrounding within one run, so a second tab costs no migration when it arrives. In v1 there is no tab bar — the Inbox list is the whole first screen and shows every conversation from every included app. When the waiting list ships (area WAIT) a two-tab bar appears with Waiting leading and Inbox second; Waiting is a filtered read of these same conversations, not a second table, so the rows, the sort (INB-4) and every rule in this section are unchanged by its arrival, and WAIT's own rules confirm or change that contract without striking through this one.
- **INB-20** The included-apps list in Settings is built from two sources only. The first is the shipped messaging-app list: the six exact package names in `lib/data/shipped_apps.dart` — WhatsApp, Messenger, Instagram, Telegram, Signal and Google Messages, the apps the spike's check 1 covers — which is also exactly what INB-16's `<queries>` declares, what CAP-1's filter defaults on, and what PERM-3's disclosure renders, with a test asserting the three are one set. The second is packages the listener has actually seen post a notification (`apps.last_seen_at`). Before dropping a notification from a package whose row is off (CAP-1), the listener upserts that package's `apps` row — package, label, `last_seen_at`, `enabled` false — and nothing else: no title, no sender, no text, no queue row (CAP-15). That row is the only thing the app keeps about an app it is not capturing from, and CAP-27's privacy policy names it. The app never enumerates installed packages, so the release build declares no `QUERY_ALL_PACKAGES` and RUN-2's permission list is unchanged (CAP-20). The consequence is printed on the screen rather than hidden: an app off the shipped list that has never posted to this phone cannot be switched on in advance, and it joins this list, off, the first time it posts.
- **INB-21** Rows group in four, and every row falls in exactly one: on with at least one message captured, by most recent captured message then by label; on with nothing captured, by label; off and seen posting, by most recently seen then by label; then the rest, by label. A test with one row in each group asserts one exact order. Alphabetical means the current language's collation (LANG-4), ties broken by package ascending. Each row carries the app's icon and label with INB-1's fallbacks, its switch, and either the number of conversations stored from it or that nothing has arrived yet; a row for an app no longer installed says so and keeps a working switch (INB-16). At first launch every shipped-list row sits in the second group. A search field appears once the list passes ten rows, and a permanent line at the bottom says why an app the user expected is missing — it appears here the first time it posts a notification — so an absent app reads as a stated limit rather than a bug (CAP-12, product principle 3).
- **INB-22** Turning a row off means the next notification that package posts after the switch moves is not stored (CAP-1), and it changes nothing on screen but the switch: its conversations stay in the list, stay openable, stay searchable and keep their chip (INB-14). The switch moving is the whole confirmation, and what it does is stated beside it. Every thread from an app whose row is off carries a standing line saying no further messages will arrive in it while the row stays off, so a thread that stopped at the moment the switch flipped never reads as a conversation that simply went quiet (CAP-12). Turning the row back on captures from that moment forward and fetches nothing from the source app; a notification from it still posted in the shade can nevertheless reach the inbox through the reconnection re-read (CAP-13), and where it does the message keeps its own `sent_at` and lands in the thread at its real time, inside a gap INB-10's notice already names. Removing the stored messages is a separate, explicit action on the same row, soft-deleting that app's conversations and their messages in one step with about five seconds of Undo (INB-6, CAP-16); a later notification revives a conversation the user deleted rather than forking a second one (CAP-23).
- **INB-23** Every spatial order this section fixes mirrors in a right-to-left language (LANG-5): the row's leading circle and trailing count (INB-1), the chip row's leading `All` (INB-14), the swipe that reveals Delete (INB-6), and the side an outbound message sits on (INB-9). Times, numbers and package names stay left to right inside them. Every control this section names — the row, the initials circle, the app-icon badge, each chip, Delete, INB-13's control, each switch — has a tap target of at least 48dp on its shorter side and a semantic label from the message files. The conversation list, the thread and the included-apps list are three of the main screens LANG-6 renders in every language at 1.3× text on a phone-size screen, and they fail on overflow.
- **INB-24** With app lock on, the conversation list, the thread, the chip row and the included-apps list are all content hidden until unlocked, and the app's preview in the task switcher shows none of them (LOCK-2, CAP-18). PERM-8's banner and INB-15's empty states may show on a locked screen, because they say only what the app can and cannot see and name no conversation, no sender and no app the user has messages from. No screen in this area writes a message's text, a sender's name, a conversation title or the device's package list to logcat, to a crash report, to a share sheet, or to any file outside the app database, in any build: RUN-2's gate and CAP-24's manifest check cannot catch a log line, so a test asserts the inbox's code paths emit none of them (product principle 1).
- **INB-25** A message captured while the app is foregrounded reaches an open list and an open thread within one second of the `EventChannel` event that carried it, with no pull-to-refresh and without leaving the screen (`docs/PLAN.md` section 4). That is the deadline INB-5's and INB-7's "arriving while the thread is open" is measured against. A message captured while the app was not foregrounded is on screen in the first frame of the list drawn after the next resume, because the queue is drained before the list reads it.

## 9. Permissions and onboarding

**Learn:** notification access is the most frightening permission an Android app can ask for, and the system page that grants it says so in the system's own words — a warning about reading every notification, with nothing about what this app will do with them. Someone who arrives there cold either refuses, and is left with an app that cannot do the one thing it promised, or grants it without understanding what they agreed to. Neither is a user we want. So the app says in its own words, before the system page and not after, exactly what it reads, that it reads from apps the person never individually named (decision 6), that nothing leaves the phone, and what it still cannot see (CAP-8, CAP-12, CAP-14).

The harder need comes after the grant. The permission can be withdrawn in system settings, the listener can be unbound, and the phone itself can stop the service without telling anyone — and a listener that silently died looks exactly like a quiet phone. The app therefore separates the three states it is actually in: access not granted, which it reads from the system; granted but not connected, which it can also read; and connected with nothing arriving, which it cannot tell apart from a weekend with no messages. It says which of those it knows, and never dresses the third up as the second. The same honesty binds the battery advice: nobody has measured what any manufacturer does to this listener — the 24-hour OEM survival check did not run (spike, 21 September 2026, check 3) — so the app offers a place to look and a detected manufacturer, and claims nothing about what a phone will do. This section owns every statement about access; the included-apps chooser is INB-20 to INB-22 and is cited, not repeated.

- **PERM-1** The disclosure screen is the only route inside the app to the system notification-access page. Every in-app entry point that would lead there — the first launch, PERM-8's banner, the Settings row — opens the disclosure first whenever access is missing, and no stored flag ever suppresses it on a tap the user made. The system's own settings app is a route the app cannot intercept; PERM-5 covers a grant that arrives that way. The screen carries one primary button (`Turn on notification access`) and one decline (PERM-4), both reachable without scrolling, and nothing else that advances: no timer, no auto-advance, no pre-ticked box, no "by continuing you agree", and no route to the system page from a link inside a longer settings list.
- **PERM-2** The disclosure states, on that one screen and in the app's own words, five things, each as its own line: what is read (the notifications the included apps post — sender, text, time, conversation); what is done with them (one inbox, answerable in place); that they stay on the phone (no account, no server, no analytics, no internet permission in the release build — product principle 1); what the app still cannot see; and that access can be withdrawn in system settings at any time (PERM-8). The fourth line names every absence CAP-12 lists, in CAP-12's order, including that an edit, unsend or deletion in the source app never reaches us (CAP-26), and adds three this area meets first: that the phone hides some messages from the app and no setting in this app can turn that off (CAP-8); that a conversation whose notification this run is not holding opens in the source app instead of answering in place (CAP-14, INB-13); and that the app cannot speak for a work profile (PERM-17). A widget test at phone size and 1.3× text (LANG-6) finds every clause in the tree with no overflow and fails when an absence is added to CAP-12 and not here; the screen may scroll, the two actions may not.
- **PERM-3** The disclosure names every app that will be captured without being chosen, rendered from the same constant the listener filters against and the chooser reads (INB-20, decision 6) and never from a second copy, with every one shown in full — no "and others", no truncation, no collapsed row. A test fails if any package can start enabled whose label the disclosure does not display. A shipped-list package that is not installed on this phone is shown like the rest, marked as not installed where INB-16's `<queries>` lets the app tell, because the point of naming it is that the user can switch it off before it ever posts. The sentence beside the list says plainly that these apps are captured as soon as they post, without the user naming them, and that the chooser turns any of them off (INB-20, INB-22).
- **PERM-4** Declining is one tap on the disclosure and leaves an app that works: the inbox, Settings, search and the included-apps chooser stay open, nothing is greyed out, no screen is replaced by a permission wall, and no feature moves behind the grant (RUN-3, product principle 3). The disclosure opens without a tap exactly once per install, on the first launch. After a decline, every later launch opens the app's normal first screen under PERM-8's banner, and from then on only that banner and the Settings row open the disclosure. That is not a stored suppression of the offer (PERM-1): the banner is always present and always opens it.
- **PERM-5** Whether access is granted is read from the system on every cold start and every resume, and never from anything the app stored: no "we sent them to settings" flag ever unlocks a screen. The process can be killed while the system page is open, and the listener can bind while the Flutter app is dead, so a launch that finds access already granted takes the app's normal launch path — which is the lock prompt while app lock is on (LOCK-2) — without ever having observed a return. Where that launch is the first on which the disclosure has never been displayed, which is what a grant made from the system's own settings app produces, the disclosure is shown once over the first screen as information: the same lines (PERM-2) and the same app list (PERM-3), with a route back to the system page beside `Continue`. Onboarding is marked done only once the disclosure has actually been on screen, so the app never captures from an app the user did not name without having said so first (decision 6).
- **PERM-6** From a fresh install the path to the system page is: open the app, the single setup page RUN-3 allows once it exists, the disclosure, its primary button, the system page — one tap on a control from the disclosure onward, and no screen in between. RUN-4's walkthrough never precedes the disclosure and never carries the grant button. A return with access still missing shows the same disclosure with one extra line saying access is still off, and the same single button (PERM-1).
- **PERM-7** The primary button tries, in order, `ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS` with `EXTRA_NOTIFICATION_LISTENER_COMPONENT_NAME` set to this app's own listener, then `ACTION_NOTIFICATION_LISTENER_SETTINGS`, and takes the first that resolves, so the user lands on one switch rather than a list to hunt through. If neither resolves — a build can ship without that screen — the button is replaced by the written path from the message files (LANG-2) and a line saying the app cannot open the page itself, never left as a button that does nothing. Three branches, three tests.
- **PERM-8** A `capture_sessions` row is opened when the listener binds and closed when it unbinds; a rebind under PERM-10 closes and reopens one like any other. While access is missing, the app's first screen draws its rows normally under a banner saying capture is off, and that banner is the screen's whole account of the state: it draws above the rows when conversations are stored and replaces INB-15's *Nothing yet* when none are. Where the newest closed `capture_sessions` row was closed on a reported disconnection, the banner says capture has been off since that time; where it was closed on a later discovery it says capture has been off since at least that time (PERM-9); where no row has ever been closed, because access has never been granted since install, it says capture has never been on and names `installed_at` rather than a time it does not hold (CAP-12). It is not dismissible, because the state it reports does not go away on being tapped; its one action opens the disclosure (PERM-1), never the system page directly; and it is gone on the first app resume or listener binding after access returns, whichever comes first. Stored messages stay readable, searchable and deletable throughout, and conversations fall back to `Open in app` (CAP-14, INB-13).
- **PERM-9** Access lost while the app is installed is written down at the moment it is observed, and the row records which observation it was. When the listener reports its own disconnection, the open `capture_sessions` row is closed inside that callback, before anything else, with that callback's time. When the loss is instead found on a resume, the exact end is unknown: the row is closed with the time of the last event the listener delivered and flagged as an estimate, and PERM-8 then says "since at least" rather than "since". The app never prints the time it noticed something as the time that thing happened (product principle 3). Not one stored message is deleted, hidden or marked unreliable — the gap is recorded, the messages are untouched (CAP-12, DEL-1). The app never re-requests access by itself, never reopens the system page without a tap, and never retries the grant in the background.
- **PERM-10** (provisional, spike check 3 — CAP-25) With access granted, the app reads on each resume whether its own listener is connected. If it is not, it requests a rebind once — at most one request per resume and at most one per 60 seconds — and waits 10 seconds; still not connected, the first screen shows the line `capture is not running right now`, with PERM-14 as its action. On a resume where the 60-second floor suppresses the request, no new wait starts and the line shows at once if the listener is still disconnected, so a first resume never accuses a listener that is merely slow to bind. The line is removed the moment the listener connects, and a connection that follows runs CAP-13's reconnection pass — the queue drained, `getActiveNotifications()` re-read, reply actions back under CAP-14 — and opens a new `capture_sessions` row (PERM-8). Whether the listener stays bound while the app is not running, whether a revocation reports itself at all, and how quickly a rebind takes effect were all unmeasured (spike, 21 September 2026, check 3), so the 10 seconds and the 60-second floor are design and are replaced by a dated measurement on hardware.
- **PERM-11** (provisional, spike check 3 — CAP-25) Silence is never reported as failure. With access granted and the listener connected, no events arriving is indistinguishable from a phone nobody has messaged, and the app never says capture stopped on that evidence (product principle 3). After 24 hours with no event of any kind — a message, a removal, anything — measured from the newest of the last event and the time the listener last connected, and with at least one app whose row is on having been seen posting since install (`apps.last_seen_at`, INB-20), the first screen shows one dismissible line: nothing has arrived since the stated time, which may be perfectly normal, with PERM-14 as its action. It shows at most once in any 24 hours and carries no error styling, no badge and no notification of the app's own. The app never states that capture is working; it states only when it last received something. The 24 hours is a guess: nobody has measured how long this listener survives on a phone trying to kill it, nor how long a real user's phone plausibly stays quiet.
- **PERM-12** A delivery check — the app posting its own notification on a dedicated minimum-importance silent channel and watching for its own listener to see it — is the only way this area turns PERM-11's unprovable state into an observed one. It needs `POST_NOTIFICATIONS`, and this area declares no permission (PERM-15), so it does not ship with onboarding: it ships no earlier than the release that first declares that permission for the first snooze (RUN-3), and until then PERM-11's line offers only PERM-14. When it ships it runs on the user's tap and never on a schedule, and cancels its notification as soon as the listener sees it or after 10 seconds, whichever comes first. Before running, it reads whether notifications for the app and for that channel are enabled and does not run if either is off, saying so — that answer is about the app's own notifications, not about capture. Seen is reported as proof, with the delivery time. Not seen is reported as exactly what was observed — this phone did not deliver the app's own notification to its own listener within 10 seconds — and never as a verdict that capture has stopped. Either result names its limit in the same sentence: it says nothing about whether another app's notification will arrive, be readable (CAP-8) or be of a shape the app stores (CAP-2, CAP-21). The listener recognises the check's own notification before CAP-1's filter runs, reports it seen and then drops it, so nothing from the app's own package ever reaches the native queue or becomes a message. Every string it shows, the channel name included, comes from the message files (LANG-2).
- **PERM-13** At most one status line shows above the first screen's rows at a time, and where more than one condition holds the first wins, in this order: PERM-8's access banner, PERM-10's `capture is not running right now`, PERM-11's quiet observation. The lower two are only meaningful when the higher state is false, so the screen never stacks a fact, a probable and an observation and leaves the user to rank them. None of the three is an empty state: INB-15's empty states draw below whichever line is showing, except that PERM-8's banner replaces *Nothing yet* outright.
- **PERM-14** (provisional, spike check 3 — CAP-25) Battery guidance is shown once, on the first launch or resume that reads access as granted while the guidance has not yet been shown, after the first screen has been drawn and never in place of it (PERM-5); the stored flag records that the guidance was shown, never the grant, so a process killed on the system page still gets it on its next launch. It stays reachable from Settings. It says only what can honestly be said: that Android and some phones stop background services, that this app cannot change those settings, which settings pages to look at, and that nobody has yet measured whether any of them keeps this app's listener alive on any phone (spike, 21 September 2026, check 3) — so it is a place to look, not a fix the app promises. It never states what any named manufacturer does to this app. Steps come from a table keyed by an exact, lower-cased match on `Build.MANUFACTURER`; each entry holds message IDs, a verification date and the device model it was verified on, never rendered text (LANG-2, DATA-1), and an entry with no verified date does not ship, so the table is empty today. Every phone therefore takes the generic branch, which opens `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` and `ACTION_APPLICATION_DETAILS_SETTINGS` for this package, neither needing a permission (PERM-15); a step whose intent does not resolve is replaced by its written path rather than left as a button that does nothing (PERM-7). The page shows the detected manufacturer as the device reported it, left to right inside a right-to-left layout (LANG-5), so an unlisted phone is visibly unlisted rather than silently generic.
- **PERM-15** Nothing in this area adds a `uses-permission` to the release build. Notification access is a service declaration, not a requested permission (CAP-20), so the disclosure, the deep link, the return check and the chooser (INB-20) change the built artifact's permission list by nothing, and `ALLOWED` in `release.yml` — empty today — is identical before and after the onboarding PR (RUN-2). Never declared by the release build: `INTERNET` (product principle 1; the debug manifest declares it for hot reload, and no release source set may), `QUERY_ALL_PACKAGES` (INB-20), `READ_SMS` or `RECEIVE_SMS`, any accessibility service, `PACKAGE_USAGE_STATS`, `SYSTEM_ALERT_WINDOW`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — PERM-14 opens the settings page rather than asking for the exemption — and `READ_CONTACTS`, since there are no avatars and no contact lookups (decision 7). `POST_NOTIFICATIONS` is declared by the release that first needs it, the first snooze (RUN-3), and PERM-12 waits for it; a fresh install that never snoozes never sees that prompt. Where a runtime prompt can no longer be shown because the system will not ask again, the offer is replaced by PERM-14's app-info route and a line saying the prompt can only be reached there, never left as a button that silently does nothing.
- **PERM-16** The PR that ships this area updates `docs/privacy-policy.md` in the same PR and does not merge without it, the rule CAP-27 sets for capture. The policy text ships inside the app and is shown in the app, translated with every other string (LANG-2), so reading it makes no network request; the hosted copy's address is shown beside it as text, and any control that opens it is labelled as opening a browser and leaving the phone — the only thing in the app that does (product principle 1). The three claims the disclosure makes — what is read, that it includes apps the user did not name, that nothing leaves the phone — exist once, as PERM-2's and PERM-3's message IDs, and the policy quotes them; a script compares the two files. The store listing and the data-safety answers are written from that same text by hand, and because `store/` is gitignored that step is a release-checklist item in `docs/RELEASING.md` rather than a CI gate.
- **PERM-17** (provisional, untested — CAP-25) The app never claims to cover a work profile or a second user on the device. Whether work-profile notifications reach the listener at all was not measured (spike, 21 September 2026, "When hardware arrives", item 5), so PERM-2's fourth line says the app cannot speak for a work profile, and no screen states that work chats will or will not appear. The mark comes off with one dated run on a device with a work profile, which replaces this rule with one saying what actually happens.

## Decisions
<!-- Numbered and dated answers to open questions, citing the rules they settle. -->
1. (21 September 2026) **No ads, ever.** The kit's starter rules ADS-1 to ADS-9 were deleted rather than struck through: they were never adopted here, and this file's own note says a starter rule may be kept, changed or deleted as long as the choice is recorded. An ad SDK collects device identifiers and brings the internet permission with it, which contradicts product principle 1 and would make the data-safety form longer than the app's whole story. A deliberate departure from the kit's default, with the reasoning in `docs/PLAN.md` section 2. PAY-5 carries the no-ads promise as a testable rule.
2. (21 September 2026) **The free tier is the whole product; Plus is extra** (PAY-4). Free keeps the unified inbox, inline reply and open-in-app, the "waiting on me" list, app lock, choosing which apps are included, and 30 days of history and search. Plus adds custom snooze times and nudges, unlimited history, rules (VIP senders, keyword alerts, mute, per-app quiet hours), the home-screen widget, export and backup, on-device summaries and reply drafts where the device supports them, and the extra themes and icons. The split is `docs/PLAN.md` section 3, and it is what PAY-4 is measured against.
3. (21 September 2026) **Plus is a one-time purchase, not a subscription** (PAY-1). Buyers of notification tools expect one-time, and no Plus capability costs anything per use, so there is no running cost to recover. A yearly subscription beside it is a decision for after launch, from the first quarter's numbers, not for v1.
4. (21 September 2026) **Sections 1 to 5 are kept as the kit wrote them** (REC, DEL, DATA, MONEY, DATE, BAK, RUN, LANG, LOCK). MONEY-1 is conditional on the app handling money and this one does not, so it never fires; it stays rather than being renumbered around. `/spec <area>` refines each section before the PR that implements it.
5. (21 September 2026) **A chat inbox with a one-line fallback, not a notification log** (CAP-2, CAP-21). Only a `MessagingStyle` notification becomes a real message; a notification from an included app whose `category` is `msg`, `social` or `email` is kept as one `raw` line rather than dropped. The narrow option was tempting and would have made the tests easier, but `docs/PLAN.md` section 9's first risk is an app changing its notification shape, and the fallback is the whole mitigation: without it that app's inbox empties silently. Capturing everything was rejected because it turns the waiting list into a feed and puts the product in the crowded notification-history category rather than the empty two-way-inbox one. The honest promise is "everything that pinged you from the apps you chose", and the store listing must say that rather than "anything that notifies".
6. (21 September 2026) **Known messaging apps are on the first time they post; everything else is off** (CAP-1). An empty list is the stronger privacy story, but it hands a new user an empty inbox immediately after the frightening permission, which is the failure RUN-1 exists to prevent, and it stops the Capture item demonstrating itself before the chooser exists. `docs/PLAN.md` PR 4 already assumed this. The cost is real and is stated rather than hidden: the app reads a notification from an app the user did not individually name, which the prominent disclosure has to say plainly before the system settings page.
7. (21 September 2026) **No avatars in v1** (CAP-9, CAP-15). `docs/PLAN.md` section 4 sketches an `avatar` column; it is dropped. A sender's photograph is the most sensitive thing the schema would hold, it belongs to someone who is not a user of this app, and it would land in every backup file and every data-safety answer. The source app's icon already tells the user which world a row came from. Adding avatars later is an ordinary migration; un-shipping them after users have data is not.
8. (21 September 2026) **A hidden message offers "open in app" only** (CAP-8). The fixture shows the redacted notification still carries a working `RemoteInput`, so this is a capability declined rather than a platform limit, and CAP-8 says so. Redaction empties the title, the sender and the self-display name as well as the text, so a reply box there sits on a thread whose counterparty the app cannot show — and the one redacted message anyone has observed was a one-time passcode. Revisit it if hardware shows redaction hitting ordinary conversations often.
9. (21 September 2026) **Six apps are captured before the user chooses anything, and a package added later is off until they turn it on** (CAP-1, INB-20, PERM-3). WhatsApp, Messenger, Instagram, Telegram, Signal and Google Messages — exactly the set the spike's check 1 is defined over, so no default-on app rests on behaviour nobody will verify. `docs/PLAN.md` section 1 names eleven things, two of which are categories rather than packages; the other five are not adopted, because eleven labels will not fit the disclosure beside its five statements at 1.3× text (LANG-6) and because each one would be a package captured unnamed and unverified. The list size is the size of decision 6's cost, and PERM-3 requires every entry to be shown in full, so the two are one constraint. A package added to the shipped constant by a later update stays off on an install that already exists: decision 6's bargain was struck at that user's first run, and switching on an app they never saw would be a grant they never gave (PERM-5).
10. (21 September 2026) **Reading a conversation is not answering it** (INB-5, CAP-22). Opening a thread marks it read; it leaves the waiting list only when it is answered or marked done. The unread badge and the waiting list answer different questions, and coupling them would let a glance at a long thread silently clear something the user still owes a reply to — which is the one failure the product's central claim cannot survive. The cost is accepted: the badge and the waiting list can disagree, and the waiting list's empty state has to say once that it is not a list of unread things. A `CLICK` removal from the source app still clears both (CAP-22), because reading it there is a stronger signal than opening it here.
11. (21 September 2026) **The battery-guidance table ships empty, and hardware fills it** (PERM-14). Every phone gets the generic Android pages and sees its own manufacturer named, so an unlisted phone is visibly unlisted rather than silently unsupported. An entry with no verified date does not ship. This is a deliberate departure from `docs/PLAN.md` PR 4, which assumed "the manufacturer-specific battery guidance ... with the exact settings path": nobody has run the 24-hour OEM survival check, so any path shipped today would be a claim about a named manufacturer that the app cannot stand behind — inside an app whose one differentiator is not doing that. The check-3 hardware run writes the first entries, each stamped with the phone and the date it was verified on.
12. (21 September 2026) **The delivery check waits for the release that already needs `POST_NOTIFICATIONS`** (PERM-12). The app cannot otherwise prove capture is still running: a listener that silently died is indistinguishable from a quiet phone, and posting itself a test notification is the only way to settle it. But `docs/PLAN.md` PR 4 reserves that permission for the first snooze, `ALLOWED` in `release.yml` is empty with a gate that fails in both directions (RUN-2), and a permission requested purely to reassure someone reads badly to a Play reviewer and to the user it is meant to reassure. Until then the app says only what it knows — nothing has arrived since a stated time — and offers the battery page. This is the weakest point in the product's honesty story and it is temporary by design; revisit it the moment the snooze release lands, when the permission is there for a real feature and the check costs nothing.

## Roadmap impact
<!-- Rules that change the data model or the build order, and where they land in docs/ROADMAP.md. Schema changes go in Phase 1. -->

Capture is the first area that stores anything, so most of what it decides is schema. These steps belong in Phase 1, beside the record-rules step and before the Capture item reads any of them.

- **Three capture tables** (CAP-1, CAP-3, CAP-4, CAP-16). `apps` (package, label, `enabled`, `last_seen_at`), `conversations` and `messages`, each carrying the REC and DEL columns. `apps.enabled` defaults on for a package in the shipped messaging-app list and off for everything else, so CAP-1 has something to filter on before the chooser exists.
- **Conversation identity** (CAP-3). `conversation_key` holds the resolved value and `key_source` names the field that produced it, with `shortcut_id`, `conversation_title` and `tag` beside them as the candidates a re-key is matched on — one column is not enough, because the field that changes is exactly the one that can no longer be matched. A unique index over (`package`, `conversation_key`) where `deleted_at` is null enforces the identity. No `group_key` column: CAP-3 removed it as a key, and the dumps show it shared across threads and changing between a notification's post and its removal.
- **Message content is typed, not flagged** (CAP-8, CAP-9, CAP-21). A boolean `redacted` cannot carry hidden, an attachment placeholder and a raw fallback at once. `content_kind` in (`text`, `hidden`, `image`, `voice`, `video`, `file`, `raw`, `other`) with `text` nullable, so CAP-8's "the marker is never stored as the message" is enforced by the column rather than by a code path.
- **Message identity** (CAP-5, CAP-8). `notification_key` and the message's index within that notification's history are stored on every message, with a `text_hash` written at capture for the cross-key match. The dedup index is unique over (`conversation_id`, `sent_at`, `sender`, `text_hash`) and does **not** exclude soft-deleted rows, because CAP-5 says a deleted message is not captured again. That column order also serves the thread view's oldest-first read and retention's range scan, so three readers share one index.
- **Search columns now, search screen later** (CAP-19). The normalised forms of message text, sender and conversation title are written at capture from the first message on. Adding them with the search screen would mean a migration that rewrites every message a user already has; only the FTS table and the screen belong in that item.
- **What the gaps are** (CAP-12, CAP-22). `installed_at` in settings, a `capture_sessions` row per listener bind and unbind, and `conversations.read_through_at` for CAP-22's read marker. Without the first two, "nothing from while access was off" is a sentence on a screen rather than a fact the app holds; without the third, the read marker arrives with Triage as a migration on live data.
- **Nothing raw survives normalisation** (CAP-15, CAP-24). The native queue holds the projected fields, not the payload; rows are deleted in the transaction that writes their message and dropped after 30 days undrained. The manifest sets `allowBackup=false` with `dataExtractionRules` excluding the database and the queue, and the release workflow checks the built manifest the way `tool/check_permissions.sh` checks permissions.

In Phase 2 the section moves three things:

- **The in-memory action map belongs to the Capture item, not Reply** (CAP-13, CAP-14). Rebuilding reply actions from `getActiveNotifications()` is the same reconnection pass CAP-13 already requires, so splitting them means writing it twice.
- **"Open in app" ships with the Inbox item** (CAP-8, CAP-14). Reply availability is state of this run, so a cold-started inbox shows "open in app" on rows before the Reply item exists. The Inbox item carries that affordance and the launcher behind it; the Reply item adds sending. Shipping the Inbox without it leaves a screen with no second tap (product principle 5).
- **Two documents change in the capture PR, not after it** (CAP-24, CAP-27). `docs/privacy-policy.md` and the store's data-safety answers, because RUN-2's gate never fires for capture.
Inbox and Permissions are the first areas that draw stored data, so most of what they decide is screens — but four things reach the schema and the build, and they belong in Phase 1 beside the capture tables, before either item reads them.

- **Per-app capture history** (INB-10, INB-22, CAP-12). An `app_capture_sessions` table, one row per enable and per disable of a source app, the per-app twin of `capture_sessions`. Without it INB-10's standing notice cannot name the date the app could first have seen anything for a conversation, nor the holes a row being toggled off leaves, and CAP-12's "none from an app whose row is off" stays a sentence on a screen rather than a fact the app holds. The `apps` table keeps its four columns; the history goes here rather than in an `enabled_at` column, because a single timestamp cannot carry more than one gap.
- **Outbound send state** (INB-9). `messages.send_state` in (`pending`, `sent`, `failed`) beside `direction`, so a widget test can seed the unconfirmed bubble the Inbox item draws and the Reply item fills. Adding it with area REP would mean a migration on live data for a column the Inbox screen already renders.
- **The shipped messaging-app list becomes an artifact** (INB-20, INB-16, PERM-3, CAP-1). `lib/data/shipped_apps.dart` holds six exact package names and is the single source CAP-1's filter, INB-21's chooser, PERM-3's disclosure and the manifest's `<queries>` all read; a test asserts the constant and the `<queries>` entries are one set, so no app is ever pre-enabled whose label and icon the build cannot resolve. `docs/PLAN.md` section 1 stays prose. The `<queries>` element gains those packages *beside* the PROCESS_TEXT entry the Flutter engine already requires — it is not replaced — and the release workflow checks the built manifest's `<queries>` against the constant the way it already checks `allowBackup` (CAP-24).
- **The listener keeps one row about an app it is not capturing from** (INB-20, CAP-1, CAP-15, CAP-27). Before dropping a notification from a package whose row is off, the listener upserts that package's `apps` row — package, label, `last_seen_at`, `enabled` false — and nothing else. That is what makes the chooser's second source exist at all, and `docs/privacy-policy.md` names it in the same PR.

- **The included-apps chooser ships with the Inbox item, not the Permissions item** (INB-20 to INB-22).
