# Product rules

_21 September 2026._

This file defines how Replybox behaves: the calculations, defaults, and edge cases behind each screen. Where a competitor was studied (see `docs/research/competitor-analysis.md`), a section says what they do, what we take from it, and our rule: we learn from their app; we don't copy its rules. Where none was, a section starts from the user need instead.

- Rule IDs (`DATA-1`) are stable: never renumber or reuse one. A dropped rule stays, struck through, with its date and reason. Tests, code comments, PRs, and roadmap items reference them.
- A rule is testable: a number, a default, an order, an edge case. "Entry is fast" isn't a rule; "a basic entry takes about four taps" is.
- "Not verified" marks competitor behavior we saw only partly.
- Every rule keeps the product principles in `CLAUDE.md`: 1. Nothing leaves the phone: no account, no server, no analytics, no internet permission in the release build. 2. Free is complete: inbox, reply, waiting list and search never move behind a payment. 3. Honest about limits: the app says what it cannot see. 4. Never hides or answers another app's notification unless the user asked. 5. Two taps to reply or clear.

## Section shape

`/spec <area>` writes a section in this shape:

> ## N. Area
>
> **They do:** what the competitor does, in our words. Parts we couldn't check: not verified.
>
> **Learn:** the user need behind it, and where they fall short.
>
> - **AREA-1** Our rule.

With no competitor studied (`docs/research/competitor-analysis.md` records that, dated), a section has no **They do** and opens with **Learn**, written from the user need itself. Never write a **They do** from what a competitor is assumed to do: the rules below it would then cite a guess as observed fact.

The sections below are starter rules that held up in an earlier app. Keep, change, or delete each one, and record the choice under Decisions.

## 1. Data foundations

**Learn:** undo, trash, backup merge, sync, and translations all depend on these being right before any user data exists.

- **REC-1** Every record has `created_at` and `updated_at`.
- **REC-2** Every record ID is a UUID v4, so records from a backup or another device never collide. Built-in defaults use fixed IDs instead, so the same default matches across devices.
- **DEL-1** Deleting sets `deleted_at`; it doesn't remove the row. Deleted records count nowhere: totals, charts, search, or export.
- **DEL-2** Delete needs no confirmation. A snackbar offers Undo for about 5 seconds. Deleted items stay in the trash for 30 days, then get purged on app start.
- **DATA-1** User-facing names of built-in items (default categories, default accounts) are translatable labels referenced by ID, never stored text.
- **MONEY-1** If the app handles money: amounts are integers in thousandths of a unit (`12.50` → `12500`), so sums never drift and every ISO currency fits. The record's type carries the sign.
- **DATE-1** A date the user picks is a local calendar date. It stays on that date if the device's time zone changes later.

## 2. Backup and export

**Learn:** a raw database file breaks across schema versions, and defaults that send data off the device cost trust.

- **BAK-1** A backup is a file with the app version and the schema version, saved or shared only when the user chooses to.
- **BAK-2** Before a restore replaces or merges anything, the app saves an automatic backup of the current data.
- **BAK-3** Merge matches records by ID (REC-2); the later `updated_at` wins, deletions included (DEL-1). The app then shows how many records were added, updated, and unchanged.
- **BAK-4** A backup from a newer schema is refused with a message to update the app. Older backups are migrated with the app's own schema steps.
- **BAK-5** Exported files use ISO dates and plain decimals with a `.`, whatever the language. Spreadsheet text starting with `=`, `+`, `-`, or `@` gets a leading apostrophe.

## 3. First run and trust

**Learn:** asking for an account, permissions, or cloud backup up front costs trust before the app has earned any.

- **RUN-1** An empty screen explains itself with one clear first action.
- **RUN-2** The release build declares no permission a shipped feature doesn't need, so the store's data-safety answers stay true. The release workflow checks it.
- **RUN-3** The first launch asks only what the device can't tell (for example the language and currency) on one page, preselected from the locale. Permissions are requested when the feature that needs them is first used, and everything else works if they're refused.
- **RUN-4** A walkthrough of up to four pages follows setup. Every page has Skip, it respects reduce motion, it can be replayed from Settings, and it shows once. An update on a device that already has data skips setup and the walkthrough.

## 4. Languages

**Learn:** a translated app only feels native when numbers, dates, plurals, search, and layout direction are right too. A cut-off label looks broken.

- **LANG-1** The app follows the device language and falls back to English. Settings offers "System default" and each language in its own name. A change applies without a restart.
- **LANG-2** Every user-facing text comes from the message files, including notifications, widgets, and generated files. Plurals and variable parts are ICU messages, never pieced-together strings. CI fails on a missing message or mismatched placeholders.
- **LANG-3** Dates, numbers, and amounts follow the chosen language's format. Files the app writes don't (BAK-5).
- **LANG-4** Search ignores case and accents in every language, including the Turkish dotted and dotless i.
- **LANG-5** Right-to-left languages mirror the layout: navigation, lists, swipe actions, arrows. Amounts, numbers, and expressions stay left to right inside them.
- **LANG-6** Translations are machine-made in the same PR that adds or changes the English message. Widget tests render the main screens in every language on a phone-size screen at 1.3× text size, and fail on overflow.

## 5. App lock

**Learn:** private data needs a lock, but a forgotten app PIN locks people out of their own records.

- **LOCK-1** App lock is off by default and uses the device's own biometrics or screen lock, so the app never stores a PIN. Turning it on or off asks for authentication first.
- **LOCK-2** With app lock on, the app asks at launch and after at least a minute in the background, and hides its content until unlocked. Notifications and widgets show no private data.
- **LOCK-3** If the device no longer has biometrics or a screen lock, app lock turns itself off instead of locking the data away.

## 6. Plus and paying
<!-- The app is free and carries no ads. A one-time "Plus" purchase unlocks the capabilities listed in docs/PLAN.md section 3. Name the screens and the locked capabilities when you /spec this section. -->

**Learn:** an ad SDK collects device identifiers and needs the internet permission, so ads would turn "nothing leaves the phone" into a false answer on the Play data-safety form and cost the app the one claim nothing else in the category can make. The free tier therefore pays for nothing, and the upgrade has to be worth buying on its own merits. A subscription to *not* see something is resented; what is sold must already work.

- **PAY-1** Plus is a one-time non-consumable purchase, not a subscription, and it unlocks every Plus capability at once. It follows the store account, "Restore purchases" sits beside the price, and the app asks the store what is owned at each launch, so a refund or a family-shared purchase lands without a reinstall.
- **PAY-2** Prices come from the store, in the buyer's currency. Never hard-coded, and nothing to do with any setting in the app.
- **PAY-3** Nothing is sold before it exists. A Plus capability that isn't finished is shown as "coming soon", with no price and no button.
- **PAY-4** Nothing that already works moves behind a payment. Paying adds what is new: the inbox, reply, the waiting list and search stay free whatever else changes (product principle 2).
- **PAY-5** Selling is quiet: one row in Settings and one small "Plus" tag on a locked capability. No interstitial upsell, no countdown, no trial that lapses into a charge — and no ad of any kind, in any build, anywhere in the app.
- **PAY-6** A purchase that fails or is left pending never charges twice and never leaves the app half-paid: the app finishes every purchase with the store whatever the outcome, including the purchase sheet being closed without buying, and nothing unlocks until the store confirms it. A store with no such product configured is a real state — show "nothing to sell yet" rather than a button that only fails.

## 7. Capture

**Learn:** the person has one phone and several apps shouting at it. What they want is not another notification log — it is to open one place, see who is waiting on a reply, and answer without hunting through six icons. What makes that tedious today is that every app keeps its own inbox, and the only thing they share is the shade, which is a pile that clears itself. The app can only ever see what the phone showed it, so the whole area turns on being exact about that boundary: capture faithfully, say plainly what is missing, and never guess at content it did not receive.

Rules marked provisional rest on behaviour measured against one app on one API level; CAP-25 says what takes the mark off.

- **CAP-1** The app stores a notification only from an app whose row in the included list is on, and the listener drops every other package before anything reaches the native queue. An app in the shipped messaging-app list (`docs/PLAN.md` section 1) is on the first time it posts a notification the listener sees; every other app is off until the user turns it on. Turning an app off stops capture from it at once and leaves what it already captured in the inbox (product principle 4).
- **CAP-2** (provisional, spike check 1 — CAP-25) A notification becomes a message only when its `template` is `android.app.Notification$MessagingStyle`. A notification from an included app with any other template is never guessed into a sender and a text: it is either kept under CAP-21 or ignored, so a promotion, a delivery update or a "backing up your photos" notice is never filed as a message. Confirmed on Google Messages and on shell fixtures at API 37 only; the other five target apps were untested (spike, 21 September 2026, check 1).
- **CAP-3** A conversation is identified by the app's package plus the first non-empty value of `shortcutId`, `conversationTitle`, `tag`. A value of `""` counts as absent, because redaction empties title fields (CAP-8); a notification supplying none of the three is keyed by its own notification `key` and never merged into another conversation. `groupKey` is never a conversation key: in the spike's dumps one `groupKey` covered three separate Google Messages threads and three separate shell threads, and one notification's `groupKey` changed between its post and its removal (spike dumps, 21 September 2026). The resolved key, the field it came from, and the other candidates seen are stored beside the conversation, so an app that changes its keying is migrated rather than split silently. Which of `shortcutId` and `conversationTitle` wins is provisional (CAP-25): no notification the spike captured carried both.
- **CAP-4** (provisional, spike check 1 — CAP-25) Every message in the notification's message history is stored as its own message with its own sender and time, not only the visible line: in a burst the visible `text` collapses to the newest message while the history keeps them all, and the inbox shows all of them. Measured on a shell-posted fixture; the one real app in the spike posted one notification per message and never a growing history (spike, 21 September 2026, check 2, fixture `shell-burst.jsonl`), so how each target app bursts is unmeasured.
- **CAP-5** A message is stored once. Within one notification `key`, a message's identity is that key plus its position in the notification's message history, so a re-post or a reconnection re-read (CAP-13) updates those messages instead of adding them — the spike's burst delivered five messages under one identical timestamp (spike dumps, 21 September 2026), so time cannot separate them. Across notification keys, two messages are the same when their conversation, sender, text and `sent_at` all match, `sent_at` being the time the posting app gave the message and never the time we captured it (REC-1's `created_at`); a hidden message is matched differently (CAP-8). The lookup sees soft-deleted rows (DEL-1): a message the user deleted is not stored again by a re-post or a re-read, and never reappears in the inbox.
- **CAP-6** A notification with `isGroupSummary` set is never stored as a message. Every group summary the spike captured carried an empty message history (spike dumps, 21 September 2026), so nothing is lost by dropping it; its children carry the content.
- **CAP-7** An ongoing notification is never stored as a message. It is a status, not something anyone is waiting on a reply to.
- **CAP-8** A hidden message is recognised from the notification's structure, never by matching the system's marker text, which is a system string that changes with the phone's language: a `MessagingStyle` notification whose message `sender`, `title` and `selfDisplayName` are all empty while its text is not. It is stored as hidden with no text, and shown with the app it came from, the notification's `postTime` as its arrival time, and only "open in app". Its identity for CAP-5 is the notification `key` plus its position in the history, never sender, text or the message's own time: that time was observed to move 19 seconds between two reads of one unchanged notification (spike dumps, 21 September 2026). A hidden notification also arrives with every action title emptied to `""`, so actions are matched by `semanticAction` and by carrying a `RemoteInput`, never by label. The marker is never stored as if it were the message, and the app never guesses what was hidden. Redaction could not be switched off on API 37 and has widened with successive Android releases, so the app treats it as a permanent condition of being a third-party listener rather than a setting a user can waive (spike, 21 September 2026, check 4, fixture `messages-redaction.jsonl`).
- **CAP-9** (provisional, untested — CAP-25) A photo, voice note or other attachment is stored as an attachment type code, never as the rendered words (DATA-1); the inbox renders that code through the message files, so the same record reads correctly after a language change or a restore (LANG-2). No media file is ever read or copied out of the other app. No attachment was captured in the spike (`docs/research/spike.md`, "When hardware arrives", item 3), so where a notification does not name the type, the placeholder says only that something arrived the app cannot show (product principle 3).
- **CAP-10** The app never posts, alters, hides or dismisses another app's notification unless the user asked for that action on that conversation (product principle 4).
- **CAP-11** A message being dismissed from the shade does not delete the stored message. The shade is the other app's; the inbox is ours.
- **CAP-12** The app has no history from before it was installed, none from while notification access was off, none from an app whose row is off (CAP-1), and no record of an edit, unsend or deletion made in the source app (CAP-26). Each of those absences is stated on screen where it would otherwise look like a bug (product principle 3, see RUN-1).
- **CAP-13** (provisional, spike check 3 — CAP-25) An event that arrives while the Flutter app is not running is appended to the native queue by the listener and handed over when the app next starts; on reconnection the listener re-reads `getActiveNotifications()` and reconciles it against what is stored, using CAP-5 to avoid duplicates. Neither half has been measured: the 24-hour OEM survival check did not run (spike, 21 September 2026, check 3), and the reconnection re-read is design (`docs/PLAN.md` section 4), not a spike result.
- **CAP-14** Whether a conversation can be replied to inside the app is a property of this run, not of the stored data: a `PendingIntent` cannot be serialised, so a reply action cannot be saved to disk. A conversation is repliable while its notification is held in this process — one that arrived since launch, or one still posted that the listener re-read on reconnection (CAP-13). Otherwise it shows "open in app". Dismissal alone never removes reply: a held action still delivered after every notification was cancelled (spike, 21 September 2026, check 5). That a restart clears the map follows from `PendingIntent` not being serialisable and was not itself measured (CAP-25).
- **CAP-15** Nothing the inbox cannot show survives normalisation. The app database keeps only the schema's fields (`docs/PLAN.md` section 4): for a message, its conversation, sender, text, `sent_at`, direction, content kind and notification key; for a conversation, its package, conversation key and the candidates that produced it (CAP-3), title and group flag. Icons, extras, channel and action objects are dropped at normalisation and never written. The native hand-over queue holds one JSON row per event carrying those same projected fields and never the notification's extras; a row is deleted in the transaction that writes its message, and a row still undrained after 30 days is dropped on the next service start.
- **CAP-16** A captured record follows the record rules: a UUID, `created_at` and `updated_at` (REC-1, REC-2), and deletion is soft (DEL-1) with no confirmation and about five seconds of Undo (DEL-2). Deleting a conversation soft-deletes it and every message in it in one step, and one Undo restores all of them; deleting a single message leaves the conversation standing.
- **CAP-17** A backup carries the included-apps list, the conversations and their messages, matched by ID on merge (BAK-1, BAK-3). A restored conversation is matched first on package and conversation key (CAP-3) and keeps the local row's ID, so its messages land in the existing thread rather than forking it or pointing at a `conversation_id` the device has never seen. Message text, sender names and conversation titles are written by whoever sent them, so every exported field goes through BAK-5's escaping, not only the fields the user typed.
- **CAP-18** With app lock on, a captured message's content is never shown in the app's own notifications or widgets, nor in the app's preview in the task switcher (LOCK-2).
- **CAP-19** Search over captured messages ignores case and accents in every language (LANG-4).
- **CAP-20** Capture adds no `uses-permission` to the release build. Notification access is a service declaration — `android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE"` on the listener `<service>`, naming the permission the system must hold to bind it — granted by the user in system settings, so it never appears in the app's requested-permission list. RUN-2's gate reads only `uses-permission` lines (`tool/check_permissions.sh`), so it never fires for capture: CAP-24 and CAP-27 are what cover capture, not that gate.
- **CAP-21** A notification from an included app that carries no `MessagingStyle` history is kept rather than dropped when its `category` is `msg`, `social` or `email`: one message of kind `raw` carrying the notification's title and text, in a conversation keyed by the package alone and labelled with the app's name, marked in the inbox as captured without a conversation. No reply is offered on it unless the notification itself carries a `RemoteInput`. Anything else from an included app is ignored (CAP-2).
- **CAP-22** A removal event is read as a signal about the source app, never as a change to our data (CAP-11). A removal with reason `CLICK` or `APP_CANCEL` marks the conversation read up to that notification's newest message and takes it off the waiting list; `LISTENER_CANCEL`, `LISTENER_CANCEL_ALL`, `CANCEL_ALL` and any unrecognised reason change nothing, because the shade being cleared is not the user reading anything. The reason comes from the removal event and is never inferred from the notification merely being gone (`APP_CANCEL` and `LISTENER_CANCEL_ALL` both observed; spike, 21 September 2026).
- **CAP-23** A notification for a conversation the user deleted revives that conversation rather than opening a second row for the same package and key (CAP-3), and files the new message in it. Messages deleted earlier stay deleted (CAP-5, DEL-1): nothing the user deleted ever returns.
- **CAP-24** The release build sets `android:allowBackup="false"` and excludes the message database and the native queue in its `dataExtractionRules`, so Android's automatic cloud backup and device-to-device transfer never copy captured messages off the phone. This is the only path data can leave the device without the internet permission, so RUN-2's gate cannot catch it (CAP-20): the release workflow checks the built manifest the way it checks permissions, and fails on a change. The only copy that leaves is a backup file the user asked for (BAK-1, product principle 1).
- **CAP-25** A capture rule that rests on an app other than Google Messages, on a notification the spike never captured, or on the listener staying alive while the app is not running, is marked provisional and names the check it waits on. The mark comes off only with a dated result on hardware, never because the feature shipped. Every fixture records the `sdkInt` and release it was captured on, and a rule stating what Android hides names that level: behaviour measured at one API level is not assumed at another. Provisional today: CAP-2, CAP-3 (the order of its top two candidates), CAP-4, CAP-9, CAP-13, CAP-14.
- **CAP-26** The app stores the text it was handed when the notification arrived. An edit, an unsend or a deletion in the source app never reaches the listener, so a stored message can differ from what the conversation now shows. The thread view says so once, above the oldest message it holds, and the privacy policy says it too (CAP-27, product principle 3).
- **CAP-27** The PR that ships capture updates `docs/privacy-policy.md` in the same PR, and a capture PR that does not touch it does not merge: what is stored (sender, text, time, conversation, source app, the conversation key and its candidates, notification key, content kind), that these are messages other people sent and they stay on the phone, that automatic backup is off (CAP-24), that stored text can be staler than the conversation (CAP-26), and notification access with what still works if it is refused. The store's data-safety answers are refreshed from that same text.

## Decisions
<!-- Numbered and dated answers to open questions, citing the rules they settle. -->
1. (21 September 2026) **No ads, ever.** The kit's starter rules ADS-1 to ADS-9 were deleted rather than struck through: they were never adopted here, and this file's own note says a starter rule may be kept, changed or deleted as long as the choice is recorded. An ad SDK collects device identifiers and brings the internet permission with it, which contradicts product principle 1 and would make the data-safety form longer than the app's whole story. A deliberate departure from the kit's default, with the reasoning in `docs/PLAN.md` section 2. PAY-5 carries the no-ads promise as a testable rule.
2. (21 September 2026) **The free tier is the whole product; Plus is extra** (PAY-4). Free keeps the unified inbox, inline reply and open-in-app, the "waiting on me" list, app lock, choosing which apps are included, and 30 days of history and search. Plus adds custom snooze times and nudges, unlimited history, rules (VIP senders, keyword alerts, mute, per-app quiet hours), the home-screen widget, export and backup, on-device summaries and reply drafts where the device supports them, and the extra themes and icons. The split is `docs/PLAN.md` section 3, and it is what PAY-4 is measured against.
3. (21 September 2026) **Plus is a one-time purchase, not a subscription** (PAY-1). Buyers of notification tools expect one-time, and no Plus capability costs anything per use, so there is no running cost to recover. A yearly subscription beside it is a decision for after launch, from the first quarter's numbers, not for v1.
4. (21 September 2026) **Sections 1 to 5 are kept as the kit wrote them** (REC, DEL, DATA, MONEY, DATE, BAK, RUN, LANG, LOCK). MONEY-1 is conditional on the app handling money and this one does not, so it never fires; it stays rather than being renumbered around. `/spec <area>` refines each section before the PR that implements it.
5. (21 September 2026) **A chat inbox with a one-line fallback, not a notification log** (CAP-2, CAP-21). Only a `MessagingStyle` notification becomes a real message; a notification from an included app whose `category` is `msg`, `social` or `email` is kept as one `raw` line rather than dropped. The narrow option was tempting and would have made the tests easier, but `docs/PLAN.md` section 9's first risk is an app changing its notification shape, and the fallback is the whole mitigation: without it that app's inbox empties silently. Capturing everything was rejected because it turns the waiting list into a feed and puts the product in the crowded notification-history category rather than the empty two-way-inbox one. The honest promise is "everything that pinged you from the apps you chose", and the store listing must say that rather than "anything that notifies".
6. (21 September 2026) **Known messaging apps are on the first time they post; everything else is off** (CAP-1). An empty list is the stronger privacy story, but it hands a new user an empty inbox immediately after the frightening permission, which is the failure RUN-1 exists to prevent, and it stops the Capture item demonstrating itself before the chooser exists. `docs/PLAN.md` PR 4 already assumed this. The cost is real and is stated rather than hidden: the app reads a notification from an app the user did not individually name, which the prominent disclosure has to say plainly before the system settings page.
7. (21 September 2026) **No avatars in v1** (CAP-9, CAP-15). `docs/PLAN.md` section 4 sketches an `avatar` column; it is dropped. A sender's photograph is the most sensitive thing the schema would hold, it belongs to someone who is not a user of this app, and it would land in every backup file and every data-safety answer. The source app's icon already tells the user which world a row came from. Adding avatars later is an ordinary migration; un-shipping them after users have data is not.
8. (21 September 2026) **A hidden message offers "open in app" only** (CAP-8). The fixture shows the redacted notification still carries a working `RemoteInput`, so this is a capability declined rather than a platform limit, and CAP-8 says so. Redaction empties the title, the sender and the self-display name as well as the text, so a reply box there sits on a thread whose counterparty the app cannot show — and the one redacted message anyone has observed was a one-time passcode. Revisit it if hardware shows redaction hitting ordinary conversations often.

## Roadmap impact
<!-- Rules that change the data model or the build order, and where they land in docs/ROADMAP.md. Schema changes go in Phase 1. -->

Capture is the first area that stores anything, so most of what it decides is schema. These steps belong in Phase 1, beside the record-rules step and before the Capture item reads any of them.

- **Three capture tables** (CAP-1, CAP-3, CAP-4, CAP-16). `apps` (package, label, `enabled`, `last_seen_at`), `conversations` and `messages`, each carrying the REC and DEL columns. `apps.enabled` defaults on for a package in the shipped messaging-app list and off for everything else, so CAP-1 has something to filter on before the chooser exists.
- **Conversation identity** (CAP-3). `conversation_key` holds the resolved value and `key_source` names the field that produced it, with `shortcut_id`, `conversation_title` and `tag` beside them as the candidates a re-key is matched on — one column is not enough, because the field that changes is exactly the one that can no longer be matched. A unique index over (`package`, `conversation_key`) where `deleted_at` is null enforces the identity. No `group_key` column: CAP-3 removed it as a key, and the dumps show it shared across threads and changing between a notification's post and its removal.
- **Message content is typed, not flagged** (CAP-8, CAP-9, CAP-21). A boolean `redacted` cannot carry hidden, an attachment placeholder and a raw fallback at once. `content_kind` in (`text`, `hidden`, `image`, `voice`, `video`, `file`, `raw`, `other`) with `text` nullable, so CAP-8's "the marker is never stored as the message" is enforced by the column rather than by a code path.
- **Message identity** (CAP-5, CAP-8). `notification_key` and the message's index within that notification's history are stored on every message, with a `text_hash` written at capture for the cross-key match. The dedup index is unique over (`conversation_id`, `sent_at`, `sender`, `text_hash`) and does **not** exclude soft-deleted rows, because CAP-5 says a deleted message is not captured again. That column order also serves the thread view's oldest-first read and retention's range scan, so three readers share one index.
- **Search columns now, search screen later** (CAP-19). The normalised forms of message text, sender and conversation title are written at capture from the first message on. Adding them with the search screen would mean a migration that rewrites every message a user already has; only the FTS table and the screen belong in that item.
- **What the gaps are** (CAP-12, CAP-22). `installed_at` in settings, a `capture_sessions` row per listener bind and unbind, and `conversations.read_through_at` for CAP-22's read marker. Without the first two, "nothing from while access was off" is a sentence on a screen rather than a fact the app holds; without the third, the read marker arrives with Triage as a migration on live data.
- **Nothing raw survives normalisation** (CAP-15, CAP-24). The native queue holds the projected fields, not the payload; rows are deleted in the transaction that writes their message and dropped after 30 days undrained. The manifest sets `allowBackup=false` with `dataExtractionRules` excluding the database and the queue, and the release workflow checks the built manifest the way `tool/check_permissions.sh` checks permissions.

In Phase 2 the section moves three things:

- **The in-memory action map belongs to the Capture item, not Reply** (CAP-13, CAP-14). Rebuilding reply actions from `getActiveNotifications()` is the same reconnection pass CAP-13 already requires, so splitting them means writing it twice.
- **"Open in app" ships with the Inbox item** (CAP-8, CAP-14). Reply availability is state of this run, so a cold-started inbox shows "open in app" on rows before the Reply item exists. The Inbox item carries that affordance and the launcher behind it; the Reply item adds sending. Shipping the Inbox without it leaves a screen with no second tap (product principle 5).
- **Two documents change in the capture PR, not after it** (CAP-24, CAP-27). `docs/privacy-policy.md` and the store's data-safety answers, because RUN-2's gate never fires for capture.
