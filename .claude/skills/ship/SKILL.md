---
name: ship
description: Pre-merge gate for a feature branch. Checks coverage of the changed files, adds missing tests, updates docs, bumps the release, drives the built app by hand, and opens the PR. Use when a branch's work is done, before asking the user to merge.
---

Stop if on `main`.

This is the longest session of the item, and every turn re-sends it (`CLAUDE.md` → Token rules). Hand the mechanical steps to a subagent, keep the judgement here, and check results with `git diff --stat` rather than by re-reading.

1. **Coverage:** run the stack's coverage-gap skill if it has one (`/coverage` on Flutter). Otherwise run `flutter test --coverage` and read the summary it prints; `coverage/` is on the deny list, so never open the raw report. For each file changed on the branch (`git diff --name-only origin/main...HEAD`, ignoring generated files), find untested logic and UI paths and add tests. A test must assert what the user would see, meaning the text on screen or inside the file. "Output exists" or "has N bytes" proves nothing.
2. **Docs in the same PR:** run `bash scripts/rules.sh` and fill the PR's "Rules" section from what it reports, rather than from memory; tick the finished `docs/ROADMAP.md` items; update `CLAUDE.md` Architecture if the structure changed, `docs/privacy-policy.md` if user data, permissions, or sharing changed, and `docs/RELEASING.md` if setup changed. Every English message has its translations. Decide the wording here, then hand the edits and the translations to a Sonnet subagent with the exact files and text.
3. **Checks:** `/verify` passes. This comes immediately before the commit in step 4, because a format check that passed earlier in the session says nothing about a file edited since, and CI's format gate is not forgiving. The format hook is not a substitute: a file written by shell redirection never triggers it.
4. **Release, if this is one:** the developer decides, not the branch — a doc fix, a refactor, or a test-only change usually has nothing to tell users and is fine left unreleased. If it does, `/release <level> --build` at the level the changes call for: it bumps the version, writes the changelog entry, commits, and — because step 5 drives the built app by hand — builds the installable artifact into `dist/`. The store's bundle can wait until it is being uploaded; CI builds both on merge. Routine enough for a subagent once the level and the entry are decided here. If not, leave the version alone; CI passes and the PR merges without a release.
5. **Drive it by hand:** install and launch the built artifact — from step 4, or `flutter build apk --release` directly if this PR isn't shipping a release (device drill in `docs/STACK_NOTES.md`; on Flutter use `/emulator`, which reads the screen as text instead of costing a screenshot per step). First write the checklist: every rule the branch claims, at most eight lines. Walk it in one right-to-left language and one theme if the app has them, and stop at about 45 tool calls — an uncapped drive cost 143 calls where a capped one cost 33. Screenshots follow the `CLAUDE.md` token rule: one per thing that has to be judged by eye, such as right-to-left layout, a chart or a theme, never one per step. Put back any user data or setting you changed. If you fix anything, go back to step 3, so the format check and the artifact both land after the fix.
6. **Platform proof:** if the branch touches native code, plugins, or permissions, check the release build's permissions against RUN-2. Run the platform CI builds on the branch: `gh workflow run ci.yml --ref <branch>`, after `git ls-remote origin refs/heads/<branch>` matches `HEAD`.
7. **PR:** push, fill `.github/pull_request_template.md` into a scratchpad file, and run `gh pr create --body-file <file>`. Use a Conventional Commits title with the version. State exactly what was driven by hand and what was only compiled. If the branch has been open a while, check `gh pr view <n> --json state` before pushing: a push onto an already-merged PR's branch misses its release.
8. Report in at most 5 lines: PR URL, version, `dist/` path, and what the user should try. Then stop: the user tests and merges. Don't merge.
